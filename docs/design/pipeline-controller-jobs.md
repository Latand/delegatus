**First selection after a restart.** Compare the subject, token and recorded owner with current state-write authority. Use the existing hot-state authority record and the same writer-readiness check that guards SQLite commits (`assertSqliteWriteAuthority`, `sqliteStateStore.ts:360–364`). When the durable active writer revision excludes the recorded owner, the authorized successor can supersede that claim immediately by keyed CAS, even if the old process lives. For same-revision owners also verify process identity in the same host, boot and PID namespace via `processIdentityStatus`. A missing process, different start identity or proven reboot establishes death. Bound the off-thread observation to 500 ms. Proven death also permits supersession on first selection, even with 170 s left. Where authority admits both or is inconclusive, a live or unverified foreign claim has its recorded deadline and monotonic cap. A traffic change or a lookup in another PID namespace alone proves neither loss of write authority nor death. A fenced successor cannot commit a permit. After logical supersession inspect the native writer, physical custody and receipt before any mutation. A surviving installer or Git child can still own an effect.

**Writes and revocation.** Factor the single-row asynchronous, deadline-aware `boundedPatchAsync` path behind `withDeliveryMutationAsync` (`store.ts:1148`) into a keyed pipeline checkpoint. **Checkout writer custody before Git registers it (phase 1).** `realExec` starts every Git child detached in its own process group (`src/lib/workflows/provision.ts:50–58`), so a `git worktree add` can keep running after a Viewer crash, and its 60 s timer (`:73–74`) dies with the Viewer. Git writes `worktrees/<name>/locked` with `initializing` only after that child has started. Between spawn and that write the add has no native evidence, and the Viewer's stripe descriptors close with the crashed process. A successor that took the free stripes and saw no checkout would dispatch a second add. The successor can be this design's controller or, after a rollback, a pre-v1 release that never reads the slot. Four rules close the interval for both:

1. **Durable intent before spawn.** The add, like the backup ref and branch mutation before it, is a mutating effect under dispatch-time authority (below). Its keyed admission records `effectAdmitted: worktree-add` with the sequence, a digest of the exact argument list, the add-fence slot and the admission time, before the child exists. The same write sets the rollback-visible deferral of rule 4. After spawn the parent records the launcher's PID and start identity in a second keyed write. The second write is diagnostic; safety does not depend on it.
2. **A fence the writer itself holds, one process group, and a bound that outlives the Viewer.** A third set of 256 stable lock files, `controller-locks/add/<stripe>`, uses the checkout stripe's hash. The job takes its slot with a nonblocking kernel lock after checkout custody and before the admission write. The supervisor starts the add through a fixed `add` entry of the shipped provisioning toolchain bundle under the serving Bun, through the same detached `realExec` spawn that starts Git today (`realProvisionExec`, `git.ts:273–275`, into `realExec`, `src/lib/workflows/provision.ts:50–58`), so it survives the Viewer and is never reaped by the helper guardian. The detached spawn makes the launcher the leader of a new process group. Only this launcher receives the add fence, through the existing `inheritFd` option of `ProvisionExecPort` (`git.ts:273`). It starts `git -c gc.auto=0 -c maintenance.auto=false worktree add …` with the admitted arguments as an ordinary **non-detached** child, so Git, and every Git child that does not start its own session, stays in the launcher's group and inherits the fence. Every stop path that `realExec` already has, the abort signal, its 60 s timer and its output limit (`provision.ts:62–79`, group kill at `:68`), therefore kills the launcher and Git together. The launcher drains Git's output itself, so Git's survival does not depend on the Viewer's pipe, and it arms a monotonic timer for the remainder of admission plus 60 s, the add's existing command bound, at which it kills its own group, Git included. The launcher therefore ends Git no later than 60 s after admission on its own monotonic clock whether or not any Viewer is alive, and 65 s is the bound the readers below use. That hard bound is what a pre-v1 reader can rely on (rule 4). Disabled automatic maintenance keeps this command from leaving a detached child that keeps the fence. Fetch, metadata, repair and tool preparation still run as plain Git children without any controller fence, and their detached maintenance keeps nothing. A repository hook that starts its own session can still hold the fence after the group is gone; rule 3 parks on it.
   - **Custody ends only at verified exit, on every stop path.** The paths are: Git exits by itself; the Viewer aborts the step (deadline, lost authority, pause, close); the Viewer's 60 s `realExec` timer fires; the launcher's output exceeds its limit; the launcher's own bound fires; the Viewer crashes or is demoted. In each, the lane leaves "Creating checkout" only through the keyed write that records the add fence **reacquired by this job** (every holder exited) together with the registration inspection of rule 3. That same write is the only one that restores or deletes the legacy deferral of rule 4. A revocation closes the job's grants and kills the group, and keeps the add admission, the deferral and the fence probe. The revoker never clears them. A crash between the kill and the verifying write leaves the deferral in place over a group that is already dead.
3. **The forward successor proves the writer exited before it decides.** On first selection of a lane whose slot holds an admitted, unconsumed `worktree-add`, the successor opens the add-fence file itself and tries the lock. If the lock is busy, the launcher, Git or a descendant of that dispatch is alive. The lane enters "Waiting for checkout writer" with the admission time, due at the launcher's hard bound (admission plus 65 s) with a 5 s probe fallback. No failure budget is charged. If the fence is still busy after that bound, a descendant that left Git's group holds it: the lane parks with `checkout-writer-unverified` and leaves the fence held. If the lock is free, every holder exited. The successor then inspects the registration and the path: a registered checkout takes the existing adoption path (`git.ts:441–463`, including `locked initializing` repair); no registration and no path prove that the dispatch made no checkout, and only then may one new add be admitted under the next sequence.
4. **A deferral the pre-v1 reader already obeys.** A pre-v1 release cannot see the slot or the add fence, and its provisioning dispatches an add before it looks for a registration (`git.ts:415–418`, adoption only after the add fails at `:441–463`). It does skip every lane whose `provisioningWait.retryAfter` is in the future (`engine.ts:11564–11571`, the wait test at `:11571`), and it schedules its next tick for that time (`controllerPass.ts:74–75`). The add admission write therefore also sets that legacy field: `retryAfter` is the admission time plus 5 minutes, which is the launcher's 65 s hard bound plus a margin of 3 minutes 55 seconds for wall-clock steps. An existing wait keeps its `startedAt`, `rounds` and budget fields. Without one, `startedAt` is that same horizon and `rounds` is zero, so the pre-v1 three-minute transient window (`PROVISION_RETRY_WAIT`, `engine.ts:3015`) starts only when the deferral ends (`nextBoundedWait` clamps a future start at `:13370`). The forward reader ignores this field for its own decision and uses the add fence. The write that consumes the add receipt, or that records a definitive no-effect observation under rule 3, restores the lane's previous wait or deletes it, as `applyProvisionOutcome` does today (`engine.ts:11693`). A pre-v1 reader started inside the horizon therefore waits; by the time it acts, the launcher has ended Git, and its add either fails on the path or branch that the first add registered (then takes its adoption path, or its `WORKTREE_INITIALIZATION_HELD` retry, `git.ts:505`, if Git left `locked initializing`) or, when the first add made nothing, is the only add that writes. That later failing add on a registered checkout is the legacy completed-checkout probe, a separate case below. A lane parked with `checkout-writer-unverified` (rule 3) leaves the `provisioning` state (`park`, `engine.ts:3494–3497`, sets `needs_decision`), and pre-v1 selects only `provisioning` rows (`engine.ts:11567`), so that park is a fence pre-v1 obeys whatever the clock says. The deferral itself depends on the wall clock, because pre-v1 compares `retryAfter` to wall time. A forward wall-clock step larger than the 3 minute 55 second margin, inside the 65 s while the first add can still be alive, after a rollback, can let pre-v1 dispatch a second add. The only pre-v1-visible fence that does not read the clock is a state other than `provisioning`, which would change the state vocabulary this design keeps, so that residual is open question 2. The version-pair acceptance steps the clock forward within the margin and records the step beyond it as that exposure.

In the crash cut where the add was spawned and is still running, neither successor makes a new add dispatch before the first one has ended, so the lane has exactly one add dispatch in total until Git has registered or provably made nothing. Peers keep moving. The orphaned launcher holds only its add-fence slot; the repo and checkout stripes closed with the Viewer, so a lane in the same repository takes them and runs its own fetch and add. Git's own lock files serialize the shared metadata, and a refusal on one of them is the existing transient `lock` class (`src/lib/git/transientFailure.ts:30,40`) with its bounded retry. Only an unrelated add that collides on the same add-fence slot waits, and it waits in the same bounded, visible step. The pre-v1 deferral applies only to the lane whose add was admitted.

**Lock ownership in all four phases.** Every kernel lock taken on behalf of a migrated job has one of two owners. The leased worker owns its native cache fence through exit of its contained installer. For a Viewer-side lock the job handle takes ownership at acquisition, before yielding, and the deadline revoker closes the parent descriptor even if the acquiring continuation never resumes. Introduce a handle method that tries the lock and registers its close action synchronously. If the permit has expired at acquisition, close immediately and return no grant. Ordinary release and revocation consume the same close-once grant. A late finally holding a reused numeric FD cannot close the successor's grant. Check the grant again immediately before dispatch. Apply this rule to nested and reacquired locks, including an outer caller's lock across a call to a job. A released parent FD can still have a live native writer sharing its open file description. Abort the owned writer, retain its identity for reconciliation and prove quiescence by reacquiring the same device/inode before authorizing another write. Fault the interval after acquisition, after child close and before receipt commit independently.

It writes the marker `node_modules/.delegatus-install-receipt.json` last (claim token, manifest digest, lockfile digest, Bun version) and publishes with one **atomic no-replace rename**: `renameat2` with `RENAME_NOREPLACE` on Linux and `renamex_np` with `RENAME_EXCL` on macOS, called through `bun:ffi` as `src/lib/runtime/attemptCopyDiscovery.ts:18–23` already loads libc and libSystem. An ordinary `rename` is never used for this publication: a directory onto an empty directory replaces it, and the clone and copy branches on main check absence and rename in separate calls (`worktreeDependencies.ts:83–84,104–105`). On 24 November, under Bun 1.3.3 on Linux ext4, a scratch probe showed both behaviours: `renameat2(RENAME_NOREPLACE)` onto an empty existing directory returned -1 and left that directory's inode and contents unchanged, and `fs.renameSync` onto an empty existing directory replaced its inode. The flag belongs to the kernel and the filesystem, so the pinned Bun changes only the FFI call; phase 1 repeats the probe under the pinned Bun 1.4.0 and on macOS. When the no-replace call reports that something exists at the path, the published path stays foreign: the scratch directory is removed, the slot records the refusal and the existing tree goes to rule 4. When the platform or filesystem does not support the call (an unsupported-flag or unsupported-operation error), or the probe under the pinned Bun fails, the lane does not stage: it takes the in-place mode below, whose exclusive `mkdir` is itself a no-replace create. The slot then records the published directory's device and inode. A partial staged tree never carries the name a reader accepts, and no publication replaces a directory that another actor created.
   - *In place*, for checkout-relative inputs (workspace members, `file:` and `link:` dependencies, patches), because Bun has to resolve those inputs in the checkout. The lane first creates the directory it will write into. One `dispatch` (`create-modules-directory`) is admitted only after `lstat` reports `node_modules` absent; the worker then creates it with an exclusive `mkdir`, which fails if anything appeared meanwhile, and writes `node_modules/.delegatus-install-intent.json` with an exclusive create: claim token, sequence and a random nonce. The admission of the install itself (`install-in-place`) records that directory's device, inode and the nonce digest in the slot before the worker runs today's command in the checkout (`git.ts:823–824`). After a zero exit the worker writes the receipt marker, which also names the nonce. These projects keep provisioning as they do on main; nothing parks for having them.
   - The in-place rules rely on Bun installing into the directory that already exists and leaving a file it does not own. One observation supports that: on 24 November, under Bun 1.3.3 on Linux, `bun install --frozen-lockfile --ignore-scripts --backend=copyfile` for a manifest with one `file:` dependency kept a pre-created `node_modules` at the same device and inode and left a foreign file inside it. Bun 1.3.3 is not the pinned runtime. Phase 1 repeats that observation under the pinned Bun 1.4.0 (`Dockerfile:6`) for a `file:` dependency and a one-member workspace before it enables rule 3b. If the pinned Bun replaces the directory or removes the intent file, rule 3b stays disabled, an interrupted in-place install takes rule 4, and the change is reported.
3. **Accept only proved trees; write only into a tree this lane created.**
   1. *Ready.* A receipt marker that matches the slot's claim, nonce where recorded, the current manifest and lockfile, in a directory whose device and inode match the slot. Or a handoff receipt from rule 4 bound to the device and inode it compared.
   2. *This lane's own interrupted in-place install.* The worker may rerun the same frozen command in place only when all of these hold: the slot holds an unconsumed `install-in-place` admission with a recorded identity; the current `node_modules` has that device and inode; the intent file in it carries the recorded nonce; and the recorded helper and its process group have exited (guardian receipt, or a verified identity that no longer runs). Bun completes its own tree and the marker follows. A tree that a rollback installer or the user created after removing this one has another inode or lacks the nonce, so it is not the lane's, whatever intent is still recorded. A pre-v1 reader never writes into an existing `node_modules`: it returns at `git.ts:809` as soon as the path exists. So a directory with the lane's identity and nonce holds only bytes that this lane's installer wrote.
   3. Every other tree is unproved and goes to rule 4.
4. **Unproved trees: verified handoff or durable refusal, bytes preserved.** For a manifest a scratch directory can reproduce, the worker performs a **verified handoff**: it installs the same inputs in a fresh scratch directory and compares the trees. When every scratch file and symlink exists in the existing tree with identical bytes, mode and link target, the slot records a handoff receipt bound to the existing tree's device and inode, the existing tree stays untouched (extra user files are allowed), and the scratch directory is removed. A difference, a manifest that cannot be staged, or a comparison that cannot finish inside the step budget ends in a **durable refusal**: the lane parks with `private-install-unverified`, the step, the tree's device and inode, and the action to inspect `node_modules` in the lane checkout and remove or complete it before retrying. Nothing in the tree changes, and no install runs in it. After the operator removes the tree, the retry starts at rule 2 with a fresh creation.
5. **Launch once, after proof.** Preparation completes only when one keyed write consumes a matching receipt marker or a handoff receipt and moves the lane to running. Until then the v1 reader shows the step "Installing private dependencies".

The only change from main for a project that provisions today is rule 4 applied to a tree that already exists at plan time: main accepts it unseen at `git.ts:809`. For a stageable manifest the handoff accepts a complete tree with no change. For a checkout-relative manifest a complete tree that predates the plan cannot be proved, so the lane parks with `private-install-unverified` and its bytes intact. This arises only when provisioning adopts an existing checkout whose `node_modules` was not made under a v1 slot, which is the interrupted-install case the refusal exists for.

The pre-v1 reader sees `node_modules` absent while a staged install is live or was interrupted, so it runs its own awaited install, and the helper never writes the name that reader checks. A pre-v1 reader can still accept a partial tree that its own interrupted in-place install left, or that an interrupted v1 in-place install left, because it accepts any existing directory without writing into it. Main behaves the same way today; open question 1 asks whether to accept that remaining rollback exposure for in-place projects. After an upgrade back, the forward reader sees either its own directory (rule 3b) or an unproved tree (rule 4), and never launches on either before proof.

Preserve user-owned data. Nothing outside the recorded scratch path is deleted, an interruption never resets `node_modules`, and the worker writes into `node_modules` only through an atomic no-replace rename or into a directory whose creation the slot proves (rule 3b), and only after a clean census (rule 0). The version-pair and regression cases below stop the installer after the scratch directory exists and before the marker, restart the controller, and observe one total checkout add, one completed install and no stage launch until the marker is verified. One version-pair case runs both interruptions on one lane, as described under "Version-pair acceptance".

Acceptance for the publication itself: hold the staged worker at a barrier immediately before the no-replace call, create an empty foreign `node_modules` from another process, and separately one holding a file, then release. Require the foreign directory's device, inode and contents unchanged, the no-replace refusal recorded in the slot, the scratch directory removed, the existing tree sent to rule 4 (a difference and a `private-install-unverified` park for both foreign trees), and zero launches before a proof exists. Run the same case with the no-replace call reported unsupported: the lane uses the in-place mode, and its exclusive `mkdir` fails on the foreign directory with the same refusal and the same unchanged bytes.

**Dispatch-time authority (phase 1).** A step permit commits the step and its deadline. It carries no authority to mutate. The Viewer-side provisioning effects (backup ref, branch mutation, `git worktree add`) take the same keyed admission in the supervisor before their command starts. Before each mutating effect of the worker (cache publication, install dispatch, link, prune, private-install publication) the worker sends a `dispatch` request that names the effect, the claim token and the next sequence, as the last frame before the syscall or child launch. The supervisor answers it from current state with one keyed conditional write: compare creation identity, lane control and delivery generations, subject fence, claim token and current step, then record `effectAdmitted` with the effect name and sequence in the slot. Only after that commit does it send `go` for that sequence. State that cannot be read inside the 500 ms admission bound, or a refused comparison, returns `stop`. The write goes through the store lease, so close, pause, hide and takeover from any process and this admission have one total order:

- Close first: the comparison fails, the worker receives `stop`, and the effect never starts. Zero new mutation.
- Admission first: the effect is admitted. The close write retires the unstarted slots, keeps this one as the compact cleanup slot, and the revoker aborts the worker and reconciles from the native receipt. An effect already admitted is never undone by guess.

A `go` or step permit is single-use, bound to its sequence and discarded after cancellation or on an older sequence, so a reply that sat in a pipe is harmless: the worker must ask again for each mutation and is answered from the state of that moment. The only in-flight window left is a `go` already committed and not yet delivered. That is an admitted effect in the same sense as the check-to-effect interval of today's `assertSetupCurrent` (`engine.ts:8698–8707`), which the 100 ms `setupWatch` poll only approximated. The dispatch admission is the same check at the same point, recorded durably, and it keeps the owner-facts rule that the consumer of an irreversible effect checks the fact is still current (see "Consistency with the owner-facts design"). The dispatch admission is the fence. The 50 ms control poll below only aborts running work such as a long install.

Acceptance: withhold the step-permit reply after its write, pause and then close the lane from another process, and deliver the reply before the control poll has run. The worker's `dispatch` must be refused and the observer must count zero new writes to the cache, `node_modules`, lock files and install children. Separately withhold a committed `go`, close, then deliver it: the effect applies once, the cleanup slot survives, reconciliation consumes the receipt and the lane is not revived. Race `dispatch` against close from two processes repeatedly and require every outcome to be one of the two orders above, never a mutation after a refused `dispatch`.

This gives two real fault seams. Wrap the supervisor's exec adapter to consume the real check-ignore child-close event and hold only its reply. The actual worker waits on that reply in every launch layout. Separately hold the supervisor's permit reply after the cache fence was acquired, before any install dispatch. Confirm contention from a second process, advance to the deadline, observe the guardian reap the worker and probe both kernel locks again. The first fault precedes cache acquisition. The second proves a stopped filesystem worker releases cache custody. In the installer control the inherited cache fence remains exclusive until the contained installer exits. Probe repo and checkout stripes separately. In the lost-reply control, deadline delivery alone must release both turns and retire all job timers while the injected await stays unresolved.

## Risks and acceptance review

- **Persisting too much work under the lease.** One bounded patch may still serialize a large lane. Measure maximum-sized lane payload, writes per successful step, state admission latency and warm loop delay. Keep coarse durable transitions and diagnostic-only inner operations. If a measured extremum breaks the existing phase budget, move preparation/serialization outside the short revision-checked commit or narrow the existing store projection before rolling out additional adapters.
- **Losing work on successful writes with lost acknowledgments.** Fault both sides separately at every effect/checkpoint pair. Verify the actual ref, job generation, commit/launch/provider receipt and lane state from a second process. A retry that silently selects a new head or reservation fails acceptance.
- **Starvation under capacity, CPU contention or resource cleanup.** Keep absolute deadlines visible, exclude confirmed CPU queue time only where the native policy already does, preserve wake/cursor fairness, and cap retry metadata. Exercise a flood of dirty lanes, long-lived shared cache writer, skipped ticks, simultaneous expiry and restart. Publish latency to an unrelated first child alongside the failing lane's latency.
- **Unsafe compatibility or misleading UI.** Refuse ambiguous legacy evidence, show the actual waiting step with its timestamp, and test full and compact readbacks during state contention. Never display success for a verified checkout whose dependencies still lack a usable receipt.

The phase-1 functional verdict requires a red base, green recovery across a fresh process, adoption of the same checkout, one first child and a visible step and age. Report the issue’s one-minute desktop acceptance as a pass or fail from the measured warm-contention workload, and repeat it in the deployment observation. Subsequent landings need their effect-specific proof, migration coverage and measured test selection. Recheck the issue's desktop condition after deployment. Scope here is the design; no implementation timing, rendered result or post-deployment acceptance is claimed.

## Open questions for the operator

1. **Rollback exposure for projects with checkout-relative dependencies.** Projects whose manifest has workspace members, `file:` or `link:` dependencies, or patches can only install in the checkout itself, because Bun resolves those inputs there. This design keeps them provisioning that way, in a directory the lane creates itself and identifies by device, inode and nonce, under a completion marker that the forward reader requires. The forward reader never launches on a tree it cannot prove, so an adopted checkout of such a project whose `node_modules` was not made under a v1 slot parks with `private-install-unverified` and its bytes intact, where main would accept it unseen. A pre-v1 release reached by a rollback cannot read the marker: if a v1 in-place install was interrupted and the operator rolls back, the old release can accept the partial tree and launch with missing tools, exactly as main does today after its own interrupted install. The options are: (a) accept that remaining exposure, which matches what main does today (recommended); (b) refuse these projects with `private-install-unstageable` and ask the operator to install by hand, which removes the exposure but parks projects that provision today; (c) design a mirrored scratch layout that stages checkout-relative inputs, which first needs proof of how Bun resolves workspaces and `file:` paths through it. The builder implements (a) unless the operator chooses otherwise before phase 1 lands.

2. **Rollback residuals that no pre-v1-visible fence can close.** A pre-v1 release reads only the ordinary lane fields, so the forward design protects a rolled-back installation with two things pre-v1 already obeys: a future `provisioningWait.retryAfter`, which pre-v1 compares with the wall clock (`engine.ts:11567–11571`), and a park, which moves the lane out of `provisioning`. Two cases remain. (i) A forward wall-clock step larger than the 3 minute 55 second margin, inside the 65 s while a v1 add can still be running, after a rollback, lets pre-v1 dispatch a second add while the first Git is alive. (ii) A pre-v1 Viewer process that still runs provisioning after the forward Viewer took write authority can start a private installer after the forward census, and for a checkout-relative project it can write into the directory the forward reader has just created, in the interval between its `lstat` and its install (`git.ts:809,823`). The options are: (a) accept both as rollback limitations, recorded by the version-pair suite (recommended: each needs a rollback during a live effect plus a clock step or two releases provisioning at once); (b) lengthen the add deferral from 5 minutes to 60 minutes, which tolerates larger clock steps but makes that one lane wait up to an hour under a rolled-back release; (c) have the add admission and the in-place install move the lane into a state pre-v1 never provisions, which closes both without a clock but changes the state vocabulary that this design keeps and shows those lanes in that state on the board while the effect runs. The builder implements (a) unless the operator chooses otherwise before phase 1 lands.

## Deferred — not currently justified

- Replacing the pipeline state machine, adding a general-purpose task queue or rewriting all of `git.ts`. Their deletion would distribute durable domain rules with no additional recovery capability.
- A release handoff command, capability manifest, installation-wide drain or first-writer gate. Reading the plan from the lane preserves the existing release handoff. The candidate verification change is confined to rehearsal and its verdict. Also deferred are changes to seat/deputy policy, stage graph, account or runtime selection, package-cache eviction, publication budgets, scratch retirement or gate evidence policy.
- A standalone dashboard, per-file progress stream, full job history and log retention system. The lane's bounded current state, most recent interruption and existing diagnostics suffice for #4290.
- A blanket one-minute deadline on healthy cold installs, queued host admission or publication. The observed desktop target is acceptance to first child under the reported contention with runnable inputs. Preserve legitimate native budgets and measure their distinct waits.
