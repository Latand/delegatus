# Pipeline controller jobs

On 20 November 2026 the requester asked that a lane which has created its checkout either start its first stage or expose the step holding it, bound the wait and recover the work. The same requirement applies to other controller jobs that perform an effect and checkpoint it later. Start with the desktop provisioning failure. Keep stage definitions, runtime choices, delivery policy and the pipeline graph intact. Source: issue #4290, opened 10:31 UTC, and its pinned controller redesign specification.

## Candidates and deletion test

The exploration followed call sites, returns, catch paths, timers and restart reads. The clearest shallow interface is the scheduling callback: the caller supplies an arbitrary closure, pool, version reader, phase barrier, recovery logic and wake policy. Tests for a pure outcome or an isolated retry formula cannot observe the interval between an effect and its consumer. Another leak is that both the scheduler and the engine interpret a process-local job list as lane authority. By contrast, a physical checkout turn and a publication lock each hide ordering knowledge that several writers would otherwise have to learn.

## Job contract

Keep an optional, controller-owned v1 record on the hot `Pipeline` JSON. Use a fixed set of slots (provision, activation, settle, publish, cloud), at most one current obligation per kind per lane. Retain the current attempt and delivery records as the authoritative domain receipts. A settlement waiting for publication can legitimately have two slots. Make kind and step discriminated unions. The public operation is small:

```ts
advanceControllerJobs(selected: SelectedLane, ports: ControllerJobPorts): Promise<Advance>
// Advance carries changed, nextDueAt and readyWork for the scheduler.
// SelectedLane identifies the row and the already admitted attempt window.
```

A job module handles one selected obligation. Internally it has a synchronous decision over a fresh row and a bounded effect adapter with a signal. Its possible decisions are to wait until a time, inspect an existing effect, authorize one step, consume evidence, or retire. Only the store adapter can mint a step permit. Only a conditional write can consume it. In phase 1 use concrete functions in `provisioningJob.ts`. Extract the shared claim/deadline/consume implementation into `controllerJobs.ts` with activation in phase 2. Keep Git, spawn, cloud and publication result types distinct.

| Stored field | Meaning and limit |
| --- | --- |
| Version, kind, subject, generation | Subject includes lane creation identity and the existing domain fence. Include stage ID, attempt number and reservation/operation ID where applicable. Generation increases on supersession. A fresh unique claim token also prevents ABA after slot removal/recreation. |
| Owner, step, stepSince, deadlineAt | Store controller release/instance and process start identity, claim token and absolute UTC deadline in the same write as the new step. An unclaimed due job has no executing owner. Within the process derive a monotonic stop time once. On recovery use the smaller of the configured step cap and the remaining wall interval. A backwards clock jump cannot renew a live claim. Test expiry at the exact deadline, process death with the clock moved in either direction and a stale timer firing after replacement. Do not refresh stepSince or extend a deadline on polls, log lines or same-step retries within a claim. |
| Status, retryAt, failure | Running, waiting for retry, reconciling or awaiting apply. Keep one previous interruption with its exact step, original start, deadline, observed time and bounded reason code. Carry it across retries and into the lane's last job result on success (one per kind). Use existing retry counters/budgets as the single source. Avoid storing argv, stderr, environment, paths copied from diagnostics or credentials in status. |
| Kind-specific evidence | Provisioning stores selected base branch/SHA/pin, exact checkout ref and start SHA, expected final head and backup ref/count where applicable. Store a compact toolchain identity/verification result and the final outcome. Other kinds reference the native reservation, commit receipt, publication operation or cloud submission key. Bound the encoded evidence per slot to 4 KiB, with bounded ref/key lengths and a 256-character redacted diagnostic. Reuse existing lane/attempt paths by reference. A field outside its validated limits yields a recorded invalid-evidence refusal before any effect. Never copy the stage graph, full attempt, transcript or Git output into a slot. |

**Writes and revocation.** Factor the single-row asynchronous, deadline-aware `boundedPatchAsync` path behind `store.ts:1147` into a keyed pipeline checkpoint. In one synchronous transaction get the current ID, compare creation, state/control generation, subject fence, claim token, current step and expected domain revision, and put the new row once. Use the existing revision/lease checks at commit. Allow unrelated row changes by rereading and applying the transition to the current row. Treat a stale subject as superseded. No Git, host call, waiting promise or external notification inside the transaction. Checkpoint the next step and its deadline **before** issuing its effect. An unavailable checkpoint authorizes zero new effects. Publish a wake after commit. The row-change trigger already publishes the dirty generation if the process dies before the wake.

On completion persist an observed receipt or consume the result with the domain transition in one conditional write. When the apply lease refuses admission, retain the previous durable step and its expected result. On the next selection re-read both the lane and the native effect. If the previous checkpoint committed and only its reply was lost, acknowledge the recorded transition. If the effect completed and its result write never committed, validate the external receipt, then consume once. On unknown external completion reconcile the same key. Retry dispatch only after a definitive no-effect observation or where the adapter proves the operation idempotent. A rejected write inside a callback has ambiguous outcome until read back. Preserve closure, pause, restart, cancellation, delivery takeover, prior attempt retirement and changes to the expected branch/head. A late positive receipt can record historical custody under the existing domain rules, never revive a superseded lane.

**Two clocks.** A pass returns on its current scheduling deadline. Its admitted job gets an independent operation lease driven by the recorded step deadline. At expiry revoke that permit, signal its owned work, record the interrupted step and reason, and enqueue reconciliation. A restart can derive expiry from the prior durable timestamp. If SQLite itself refuses the timeout write, the *already recorded* expired step remains readable. Stop effects immediately, schedule a bounded state retry, and checkpoint the reason against that same claim at the first successful admission. Each state attempt uses `min(remaining, 500 ms)` with asynchronous admission and yields to peers on refusal. The watchdog/fair cursor remains a crash fallback. Store outage cannot support a promise of a new durable write while the disk is unavailable.

**Capacity and cleanup.** Replace repository/predecessor and nested publication promise waiters with a durable wait reason and due time. At admission try the physical turn and the pool without blocking. A refusal releases execution capacity and retries on owner release or due time. Preserve FIFO ordering among contenders for the same common dir by original wait time plus lane order, with bounded indexed selection if a busy repo would otherwise refill every slot. Release the common-dir turn after verified checkout, keep checkout custody through tool preparation. Preserve alias and unknown-path exclusion. Thread release and claim comparisons through success, failure, abort and finally. Bound active executors to four provisioning, four publication and four shared settlement/setup/cloud jobs per Viewer as today. Stop reads retain their separate four. Keep the existing inline fast path for ordinary native activation within its selected lane. If that call outlives the pass, retain at most four such claims executing on this Viewer and let the next selection reconcile the oldest due one; the setup pool is independent. Serialize additional eligible subjects of a kind by the existing attempt cursor. A later selection may consume a fresh slot after the previous subject retires. One process-local handle per admitted slot, bounded by those caps. Rows waiting on an effect or CPU ticket consume no local promise chain. Advance the dirty/due/fair cursor even when capacity is exhausted.

A deadline revokes **write permission** immediately. Releasing a slot or superseding a token alone cannot prove a process has stopped writing a worktree. Propagate the signal and remaining timeout into `realExec`, filesystem loops and every acquisition. Allow a revocable read's late reply to be discarded. For an already-dispatched mutator retain its physical fence through child close, including inherited descriptors. For toolchain filesystem work without cancellable syscalls, run the preparation in an owned helper from the **serving release**, using the existing dependency implementation, bounded output, process identity and a checkout lock inherited by children. The helper sends the static next step and claim token to its supervisor and waits for the supervisor’s durable acknowledgment before starting that step. A closed channel revokes further work. Reuse the installed Bun and shipped helper code in checkout and packaged installs; test both launch roots. Carry the cache lock as the additional FD. No code from the selected worktree defines the helper. Enforce the same custody on checkout mutation and recovery across a controller crash. On Windows use supported process/lock ownership proofs and preserve interrupted installs for inspection per the package design. Bound the cleanup observation (5 s per observation), leave the original owner/lock discoverable if still held, release the scheduling slot, then recheck on a due tick. No second writer enters a held physical checkout. Bound detached handle retention too: unresolved live owners count against the owned-process cap until close/proved dead. Re-read custody on a later pass even while capacity is full. For lost-reply tests, hold only the reply after recording the actual child-close event; reconciliation must then release custody immediately. For the inverse control, hold an inherited writer FD after the parent exits; release must wait for that writer. A wedged kernel operation may delay that resource's reuse. The board must still show the reason and age and independent work must progress.

**Selection.** Keep `pipeline_tick_work`, its generation, due index and fair cursor. Fold the earliest step deadline, reconciliation or retry time into `acknowledgePipelineControllerWork` alongside existing domain waits. Check already-due values as ready. Post a coalesced timer for the earliest due time, reconstruct it with the indexed scheduler at boot, and request an immediate turn after successful consume. Ignore a live handle only for duplicate *execution*, never for expiry or control reconciliation. Remove blanket job-ID exclusions in `controllerPass.ts` and the scoped main walk (`engine.ts:14613`); keep stop-read exclusion for its independently bounded transfer. Prevent a busy loop by acknowledging observed generations and waiting until due for unchanged claims. A pass selects at most four lanes, each with the current attempt plus its existing window. For each lane inspect the fixed slots once, no full registry read, job-table census or per-file heartbeat writes. Hold at most one timer for the next scheduler wake, plus timers for admitted work.

## Risks and acceptance review

- **Persisting too much work under the lease.** One bounded patch may still serialize a large lane. Measure maximum-sized lane payload, writes per successful step, state admission latency and warm loop delay. Keep coarse durable transitions and diagnostic-only inner operations. If a measured extremum breaks the existing phase budget, move preparation/serialization outside the short revision-checked commit or narrow the existing store projection before rolling out additional adapters.
- **Losing work on successful writes with lost acknowledgments.** Fault both sides separately at every effect/checkpoint pair. Verify the actual ref, job generation, commit/launch/provider receipt and lane state from a second process. A retry that silently selects a new head or reservation fails acceptance.
- **Starvation under capacity, CPU contention or resource cleanup.** Keep absolute deadlines visible, exclude confirmed CPU queue time only where the native policy already does, preserve wake/cursor fairness, and cap retry metadata. Exercise a flood of dirty lanes, long-lived shared cache writer, skipped ticks, simultaneous expiry and restart. Publish latency to an unrelated first child alongside the failing lane's latency.
- **Unsafe compatibility or misleading UI.** Refuse ambiguous legacy evidence, show the actual waiting step with its timestamp, and test full and compact readbacks during state contention. Never display success for a verified checkout whose dependencies still lack a usable receipt.

The first landing is accepted when the phase-1 regression fails on the base and passes across a fresh process, the same worktree is adopted, the first stage starts within the issue's minute under the specified contention, and the board exposes step and age. Subsequent landings need their effect-specific proof, migration coverage and measured test selection. Recheck the issue's desktop condition after deployment. Scope here is the design; no implementation timing, rendered result or post-deployment acceptance is claimed.

- Changing release succession, seat/deputy policy, stage graph, account or runtime selection, package-cache eviction, publication budgets, scratch retirement or gate evidence policy.
- A standalone dashboard, per-file progress stream, full job history and log retention system. The lane's bounded current state, most recent interruption and existing diagnostics suffice for #4290.
- A blanket one-minute deadline on healthy cold installs, queued host admission or publication. The observed desktop target is acceptance to first child under the reported contention with runnable inputs. Preserve legitimate native budgets and measure their distinct waits.
