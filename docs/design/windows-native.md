# Native Windows feasibility

## Decision and evidence boundary

Native Windows has substantial infrastructure on main. A supported installation that launches agents and their Delegatus tools still needs a small, measured completion effort. Recommend the scoped plan below, starting with a real package boot in Windows CI. There is insufficient evidence to publish a supported launch procedure today.

This assessment reads main at `836c8498ef913ad94d1d79c51c8b01d53b30d01b`, confirmed against the forge on 2026-10-15. All source references below use that revision. The research checkout stayed at its starting main revision `f4dc29d297708e4af257c9a265efd3c2c9f949c2`; the intervening #2923 change was inspected through `gh`, and its changed state-store source was reread to update the affected references. Other cited files were unchanged. GitHub searches, workflow definitions and completed job logs were read through `gh`. No workflow was dispatched or rerun, no provider generation was purchased, and no product process was started. The research environment is Linux. Windows execution evidence comes exclusively from the cited hosted jobs; no interactive Windows installation or authenticated Windows agent session was validated.

The initial support target is a foreground native Windows x64 package installation, loopback access, one existing Claude Code account and the Delegatus MCP actions required for orchestration. Git for Windows and its Bash can be prerequisites without introducing WSL. Headless CI can prove package boot and synthetic provider interactions. An actual authenticated Claude turn and desktop behavior remain release acceptance checks on a Windows machine.

Main's README already says native Windows runs Claude Code only (`README.md:63`), and the guide excludes Codex, managed accounts, local dictation, MCP and `--tailscale` (`docs/guide/getting-started.md:49-62`). The earlier WSL-only compatibility description supplied with the request is stale at this revision. The guide's Claude claim exceeds the current integrated Windows evidence: account credential checks and child environments still carry the blockers described below.

## What a native installation would execute

`bunx delegatus-cli`, or an installed `delegatus` command, enters `bin/cli.mjs`. The launcher chooses Bun for both child processes, starts the runtime host, checks its owner/readiness, then starts the Viewer and checks HTTP readiness (`bin/cli.mjs:665-720`, `:1171-1245`). The Viewer is the Next server; the runtime host owns the journal and structured engine consumers. Claude runs as a child with stream JSON over stdio. Codex runs an app-server child over stdio on current main. Agents normally start the bundled MCP server as another Bun process. None of this foreground package path requires a Linux container.

The classifications apply to the stated operation. **Works** means the named mechanism has Windows CI evidence. **Works with caveats** means partial coverage or a documented limitation. **Blocked** means a supported claim requires a concrete repair or an unmet integration acceptance; it does not assert that every attempt to start the executable fails.

Sizes are relative engineering scope: S is one bounded seam with focused checks; M crosses a few existing seams and their integration. These are proposed follow-up changes. This research authorizes no implementation. Run the slices in order; each later slice depends only on the applicable earlier results. Repair a measured failure at its existing seam before extending coverage.

The Windows launch procedure to validate in slices 1 and 5 is deliberately narrow: install the supported Bun version, Git for Windows and native `claude.exe`; sign into Claude from the user's terminal; install the verified Delegatus package; start `delegatus --no-open` in the foreground; open the loopback URL the launcher prints; use Main; stop from that same terminal. Use an exact package version for acceptance. No exact version is designated supported by this document. The repository's current shell installer snippets and Linux background-start instructions are not a validated PowerShell procedure.

Manual package upgrade/relaunch is sufficient for the first supported procedure. Auto-update and rollback of the actual application require a later Windows package A-to-B acceptance; the existing fixture custody tests are retained. Native source prepack needs the same JS-entry resolution the CLI already uses if native packing is subsequently required. Neither task needs to precede validation of a published tarball.

Treat #1663 as a small parallel reliability repair in its existing work item: preserve timeout/missing-command/exit/parse causes, make preflight report the actual cause, and allow a bounded cold-start attempt. Windows CI can inject those outcomes and require a successful live snapshot. Keep empty or unreadable snapshots from implying that an owned process is proven dead. Do not bundle a process-reader rewrite into the launch work.

Respect the limits constraint: use one smoke job with existing build artifacts, synthetic providers, explicit test paths and bounded deadlines. Reuse the current platform, launcher and runtime verification code. Linux lifecycle checks use the project's owned gate with isolated HOME, config, temporary and state roots. Windows lifecycle checks use its existing guardian. No whole-directory test sweep, repeated blind CI rerun, paid provider campaign or new portability framework is needed.

## Deferred — not currently justified

- Native Codex product support and restart-surviving callbacks. Reassess after #2922 lands; this document makes no claim about the provider's general Windows support.
- Managed account provisioning, in-app login supervision, local dictation, Tailscale, App-scoped forge credential shims, image attachments and desktop integrations. Validate the selected provider's real layouts before expanding the launch contract.
- ConPTY, a tmux replacement, a Windows service installer, systemd/nsenter emulation and native blue/green Docker deployment. Foreground package launch avoids those dependencies.
- Replacing agent tree termination with Job Objects, porting all resource containment, open-handle enumeration, and full scratchpad slug recovery. Preserve the existing limitations and worker Job Object implementation; a demonstrated launch defect can justify a separate slice.
- Multi-user Windows security claims, ARM64 and 32-bit targets, network shares, and universal case-folding/path rewrites. The selected runner evidence is Windows x64 with one account.
- Automatic updates of the real Windows application and native source packing. Retain manual package upgrade until an actual A-to-B package rehearsal exists.

The proposed work serves the quoted requirement through native Windows processes and an explicit foreground launch path. It reuses the existing Windows backend and limits the first completion to one engine/account. No hard-to-reverse architecture choice or ADR is required.
