## 1. Which engine path runs the tools

Two ways to let the ephemeral agent use the claimed reads:

**A. Structured tool exposure.** Hand each CLI the claimed tools as native
tools, through an MCP server the install ships, and let the engine's own
loop call them; the MCP server POSTs `/tool-calls`.

**B. A runner-driven call/answer loop.** Each round is one ordinary
`runEphemeralAgent` run whose JSON schema gains a fourth action, `call`, with
up to four `{tool, arguments, cursor}` items. The runner sends those calls,
waits out `pending`, and starts the next round with the results added to the
prompt. The last round offers only the slice 1 actions.

| | A. native tools via MCP | B. runner-driven rounds |
|---|---|---|
| Answer profile (§B.6) | Must be widened on both engines: Claude loses `--strict-mcp-config` with no servers and the init check that lists exactly `StructuredOutput` (+ `WebSearch`) (`progress.ts:46-58`); Codex needs an `mcp_servers` entry under `--ignore-user-config` and a tripwire that admits MCP items (`progress.ts:19-25`). Every probe of §B.11 tests 7, 8 and 25 has to be redone. Codex models are `code_mode_only` (memory above), so the exposure path itself is uncertain. | Unchanged. Same argument lists (`ephemeral.ts:165-184`, `:204-266`), same tripwire, same probes. Only the JSON schema and the prompt differ. |
| Credential and lease | Must reach a process the model drives. Today the credential is scrubbed from the child (`ephemeral.ts:70-71`). | Stay in the Viewer process; the child never sees them. |
| Bounds (8 rounds, 4 per round, 16 total) | Enforced indirectly, by the MCP server refusing; the engine decides how many calls a turn issues. | The runner counts rounds and items directly. |
| Pending and polling | Inside one blocking MCP call. | In the runner, between rounds. |
| Audience gate | In the MCP server, before the engine sees a result. | In the runner, before the next prompt is built. |
| One choke point for 2b (actions alone, `outcome_unknown`, `confirmation_pending`, hand-off after an action) | Split between the MCP server and the runner. | All in the runner. |
| Latency and cost | One model session. | One CLI start per round (a few seconds each) and the prompt re-sent each round; the prefix is identical from round to round, so provider prompt caching applies. With the typical one or two call rounds this adds two to three starts. |
| Code | An MCP server entry point (with its own state-owner claim, AGENTS.md "Only a declared owner…"), a per-engine config path, new probes. | One new module, a schema, a prompt section, a runner restructure. |

**Decision: B.** The answer profile is the hardened part of the relay and
both engines' proofs rest on it; B leaves it byte-identical and puts every
call, count and audience decision in one place in the Viewer, which 2b
needs too. A is cheaper per answer in latency, and that is its only
advantage; it is recorded under Deferred with the condition that would
reopen it.

## 2. The loop

`runClaimedRequest` (`runner.ts:145-457`) keeps every step before launch
(validation, target, member limit, drain, run ledger, account) and every step
after the decision (`finish`, `complete`, records, cleanup) unchanged. Only
the part between launch and decision, `runner.ts:291-403`, changes shape.

```
tools = callableReads(request)                 // §2.1
if tools is empty: slice 1 path, unchanged     // §8
lease = leaseKeeper(...)                       // heartbeats for the whole request
results = []                                   // what the model has seen
for round in 1..8:
  final = round == 8 or callsLeft() == 0 or terminalSeen
  out = runEphemeralAgent(round prompt, final ? handoffAnswerSchema : roundSchema(tools))
  if lease lost: return null                   // as today, runner.ts:403
  if out is reply / ignore / handoff: decision; break
  if out is call (only when !final): results += runCalls(out.calls)   // §3
decision → the slice 1 completion builder (runner.ts:404-429), unchanged
```

### 2.1 Which tools the agent may call

`callableReads(request)` (new, `toolLoop.ts`) returns the items with
`mode: "direct"`, `effect: "read"` and a `parameters` object, minus any item
whose `audience` the requester lacks (§6). An item with `effect: "action"`
is never callable in 2a: I3 sends actions only with F2, which this install
does not list, and if one arrives anyway it is treated as a hand-off item.
2b changes exactly this function (§10).

### 2.2 The lease keeper

Today the heartbeat timer and stall check live inside one child's lifetime:
the first beat is awaited after launch (`runner.ts:387-388`), the interval is
cleared when the child exits (`runner.ts:389-400`), and a lost lease cancels
that child (`runner.ts:373-379`, `:350-355`). The loop needs the same
heartbeat across every round and every call phase between rounds (L4: calls
never extend the lease).

Lift `beat`, `cancelStalledRun`, the timer and `newestProgress` out into a
closure created once per request, before round 1, and stopped in the
`finally` of `runner.ts:439`. It holds:

- the current child's `cancel` (set per round) and one `AbortController`
  whose signal every `/tool-calls` request carries (`relayCall` already takes
  `signal`, `client.ts:68`);
- `lost`: set by a heartbeat answered 404 or 409 `lease_lost`, by a stall
  past `stall_window_s`, and by a `/tool-calls` answered 404 or 409
  `lease_lost` (E1). Setting it cancels the child and aborts the calls;
- `acked`: true after the first acknowledged heartbeat. The other side
  accepts calls only after heartbeat `seq: 1` (their §3.9), so the first call
  of a request waits for `acked` and sends one beat itself if needed.

The slice 1 path uses the same keeper with one round, so there is one
heartbeat implementation. Its wire behaviour (seq order, interval, progress,
stall) is what `runner.test.ts:128`, `:212`, `:236`, `:364`, `:454` and
`:552` already pin, and they keep passing unchanged.

### 2.3 Rounds and the child

- Each round runs `runEphemeralAgent` with `key: external-relay:<request>:<round>`
  (`headless.ts:394` refuses a key that is still registered) and
  `runDir: <runDir>/round-<n>`, so a Codex `answer.json` left by round *n*
  can never be read as round *n+1*'s answer (`ephemeral.ts:202`, `:371-372`).
  The request's `runDir` is still removed in `finally` (`runner.ts:449-450`).
- `changeRun` records each round's child pid and identity
  (`runner.ts:331-348`), so the orphan sweep (`poller.ts:72-112`) kills
  whichever round is live.
- `recorder.begin` runs once, at the first launched child (`runner.ts:330`).
- The hard cap stays per child (`target.hardCapMinutes`, `runner.ts:309`); it
  is the stuck-child guard of §A.6 L4. The loop's total is bounded by eight
  rounds and by the per-call deadline of §3.3.
- A drain that starts mid-loop does not stop it: an answer admitted before a
  drain completes normally (`runner.test.ts:719`).
- A round that ends `failed`, `timeout`, `violation` or `cancelled`
  completes exactly as slice 1 maps it (`runner.ts:417-428`). A round answer
  that fails the round check (below) completes `failed` / `invalid_answer`.

### 2.4 The round schema

Closed, every property required, no length keywords: the same constraints
that make `answerSchema` acceptable to Codex strict mode (relay.md §A.8,
`protocol.ts:165-174`).

```json
{
  "type": "object",
  "additionalProperties": false,
  "required": ["action", "text", "reply_to", "calls"],
  "properties": {
    "action": { "type": "string", "enum": ["reply", "ignore", "handoff", "call"] },
    "text": { "type": "string" },
    "reply_to": { "type": ["string", "null"] },
    "calls": {
      "type": "array",
      "items": {
        "type": "object",
        "additionalProperties": false,
        "required": ["tool", "arguments", "cursor"],
        "properties": {
          "tool": { "type": "string", "enum": ["<callable read names, sorted>"] },
          "arguments": { "type": "string" },
          "cursor": { "type": ["string", "null"] }
        }
      }
    }
  }
}
```

- `arguments` is a JSON object written as a string. Strict mode refuses a
  free-form object property, and each tool's own `parameters` schema reaches
  the model in `<tools>` instead. The runner parses it; the other side
  validates it against `parameters` (R3 `invalid_arguments`).
- `cursor` non-null asks for the next page of an earlier truncated result;
  `tool` then names that result's tool and `arguments` is ignored.
- The final round uses `handoffAnswerSchema` (`protocol.ts:177-183`)
  unchanged, so the decision that leaves the loop is checked by
  `checkedAnswer` (`protocol.ts:195-226`) exactly as in slice 1.
- `checkedRound(value, request, tools)` (new, `protocol.ts`) returns either
  `{kind: "calls", calls}` or the `checkedAnswer` decision. `action: "call"`
  with an empty `calls` list counts as a round with no calls, and the next
  round is final.

### 2.5 The round prompt

`toolRoundPrompt(request, round, state)` (new, `prompt.ts`) builds on the
same sections as `answerPrompt` (`prompt.ts:3-37`), which itself stays
byte-identical (§8). Differences, all only in loop mode:

- The `<tools>` section carries the direct items with `effect`, `parameters`
  and `audience` as received (zod keeps them once the schema declares them).
- `<tool_guidance>` follows `<tools>` as a JSON string when
  `input.tool_guidance` is non-null (I4).
- `<tool_results>` follows from round 2: a JSON array, one entry per call so
  far, in round order and in each round's item order:
  `{round, tool, arguments | page_of, status, output, truncated, next_cursor?, audience?, code?}`.
  `call_id`, `effect`, `delivered`, `replayed` and `calls_remaining` stay out:
  the model needs none of them.
- The first frame paragraph names `<tool_guidance>` and `<tool_results>` among
  the sections that are data written by other people. All sections keep the
  `<` → `<` escape (`prompt.ts:2`).
- The actions paragraph replaces "You cannot call any of those tools"
  (`prompt.ts:27-28`) with: tools with mode `direct` and effect `read` can be
  called with action `call`, at most `n` this round (`n = min(4, calls left)`),
  results arrive in the next round; identical calls return the same stored
  result; a truncated result's `next_cursor` fetches its next page; `handoff`
  remains for what needs a hand-off tool; this is round `k` of 8 and `c`
  calls are left; results with an `audience` are for that audience only.
  The final round says no more calls can be made. When
  `answer.progress` is `"notes"`, every round keeps the one-line note
  instruction.

## 3. One call, on the wire

`runCalls(calls)` (new, `toolLoop.ts`) takes a round's items in order.

### 3.1 Local checks, before anything is sent

Each of these becomes a result the model sees, with a wire code, marked
local, sent nowhere and counted nowhere:

| Condition | Result |
|---|---|
| Item past `min(4, calls left)` in this round | `denied` / `too_many_calls` |
| `tool` outside `callableReads` (defence; the schema enum already restricts it) | `denied` / `not_permitted` |
| `arguments` is not a JSON object, or the body exceeds 65 536 bytes (C1) | `denied` / `invalid_arguments` |
| `cursor` was never returned in this request | `denied` / `invalid_arguments` |
| Same logical call already answered in this request | the stored result again, no request |

Arguments are not validated against `parameters` locally: the other side's
validator is the authority, and a second validator that disagrees with it
would refuse valid calls (Deferred).

### 3.2 Body and `call_id`

```
logical  = {tool, arguments}         or  {cursor}
canonical = JSON with keys sorted at every depth, no whitespace, UTF-8
call_id  = base64url(sha256("delegatus-relay-call\n" + request_id + "\n" + canonical))   // 43 chars
body     = {lease_id, call_id, tool, arguments}   or   {lease_id, call_id, cursor}
```

`arguments` is sent in its canonical form, so every send of one logical call
is byte-identical apart from `lease_id`. The key order matches
`tool_call_bodies.json`. The id matches `^[A-Za-z0-9_-]{22,64}$` (C3), is
unique per logical call in the request, and needs no storage (§4).

### 3.3 Sending, polling, retrying

`POST {api_base}/requests/{id}/tool-calls` through `relayCall`
(`client.ts:62-160`) with `timeoutMs: 30_000` (the other side answers within
20 s, L3; the default is 5 s, `client.ts:155`), `maxBytes: 65_536` (B1) and
the keeper's signal. Up to four calls of a round run concurrently (L2).

| Outcome | Action |
|---|---|
| 200, parses as `ToolCallResult` (§9), `status: pending` | Wait `retry_after_s` (1–60), send the identical body again. Polls do not count (L1). Stop polling 330 s after the first send, 30 s past the other side's 300 s deadline (L3), and give the model a local `error` "The read did not finish." |
| 200, `denied` / `unavailable` | Wait `retry_after_s` and resend the same body, at most twice (R3); then hand the denial to the model. |
| 200, any other status | The result, after the audience gate (§6). |
| 200 that fails the result schema | Treated as a transport failure below; the identical body is safe to resend (C4). |
| Network error, timeout, 5xx, `413 too_large` on the response size | Resend the identical body after 1, 2, 4 s; after three failures the model gets a local `error` "The call could not be completed." |
| 429 `rate_limited` | Wait `retry_after_s` (cap 60 s), resend. Counts toward the three tries. |
| 404 `not_found`, 409 `lease_lost` | Lease lost: the keeper cancels the round and aborts the calls; the request ends with no completion, as a lost heartbeat does today (`runner.ts:373-379`, `:403`). |
| 409 `call_conflict` | Cannot happen with §3.2 ids; if it does, the model gets a local `error` and the id is never sent again. Logged without arguments. |
| 400 `malformed`, 413 `too_large` (request) | Local `error`; no resend. |
| 401 `unauthorized`, 426 `unsupported_version` | No further calls in this request; the next round is final. |

Every outcome above reaches the model as a result, and the final answer then
goes out through the slice 1 completion path, so a request that started a
loop always ends with one completion or, when the lease is gone, with none.

### 3.4 Progress

A call sends `tool_start` and `tool_done` progress with `tool` set to the tool
name, through the keeper's `newestProgress` and `noteRelayProgress`
(`runner.ts:312-318`), only when `answer.progress` is `"notes"` and the tool
carries no `audience`. A restricted tool's name stays out of the chat's status
line.

## 4. Identity, idempotency and lease loss (C3, C4, C6)

The wire puts the call ledger on the other side, keyed by
`(request_id, call_id)` and independent of the lease (C6), and compares
bodies without `lease_id` (their `relay_v1.json`, `ToolCall.description`:
"Identity excludes lease_id for re-claim replay"). The install's half is to
send the same `call_id` for the same logical call every time, and §3.2 does
that with a pure function of the request id and the canonical body:

- **Retry and poll** inside one run: the same id and the same bytes (C3).
- **The model repeats a call in a later round**: the runner's per-run map
  answers from the result it already holds, with no request.
- **Viewer restart mid-loop**: unchanged from slice 1. The orphan sweep kills
  the child and completes `failed` / `install_restarted`
  (`poller.ts:72-112`); nothing resumes from local state.
- **Lease lost, then the request is offered again** under a new lease: a fresh
  run starts (`runner.ts:166` admits it once the old run has dropped its
  ledger entry). Any call the new run's model makes with the same tool and
  arguments gets the same `call_id`, and the other side answers with the
  stored result and `replayed: true`, never executing it again; its earlier
  calls still count toward L1 and B2, which the next `calls_remaining`
  reflects. Under §A.6 and §A.9 of `relay.md` a lost lease falls back and the
  request is never offered again, so today this path exists for C6's sake;
  it costs nothing because the ids need no storage.

A persistent install-side call ledger was considered and cut: it would hold
state that the other side already holds, and every case above is covered
without it (Deferred).

The run record of a re-claimed request: `countMemberAnswers`
(`answers.ts:319-345`) counts record files, so a request run twice would count
twice against the member. 2a counts each `requestId` once there (one `Set` in
that loop).

## 5. Budgets and truncation

| Bound | Where it is enforced |
|---|---|
| ≤ 8 rounds | The loop counter; round 8 gets `handoffAnswerSchema`. At most 7 rounds can call. |
| ≤ 4 calls per round | §3.1, and `n` in the prompt. |
| ≤ 16 calls per request (L1) | The other side counts; the runner keeps `callsLeft = min(lastFresh.calls_remaining ?? 16, 16 - newIdsSent)`, where `lastFresh` is the newest result with `replayed: false` (a replay carries the count from when it first ran, X1 `replayed`). `callsLeft = 0` makes the next round final; a `too_many_calls` denial does the same. |
| ≤ 4 in flight (L2) | One round's calls only, ≤ 4. |
| 20 s / 300 s per call (L3) | §3.3 polling with the 330 s guard. |
| ≤ 16 000 code points per output, ≤ 65 536 bytes per response (B1) | The other side cuts; the runner refuses a larger response (`maxBytes`) and, as defence, cuts an `output` over 16 000 code points before it reaches the prompt. |
| ≤ 65 536 bytes of output per request (B2) | The other side denies `quota_exhausted`. The runner counts the UTF-8 bytes of each distinct `call_id`'s outputs and stops adding past 65 536, so the prompt can grow by at most that much plus the call echoes. |
| Truncation and paging (B3) | `truncated: true` with `cursor` reaches the model as `next_cursor`; the model decides whether a page is worth a call. A page fetch is a new logical call `{cursor}` with its own `call_id` and counts (L1). A last page ends with `"\n[Truncated]"` and has no cursor; it is passed on as is. |
| Prompt size | Claim (≤ `max_response_bytes`, ≤ 1 MiB) + ≤ 64 KiB of outputs, on stdin as today. |
| Answer length | `answer.max_chars`, `checkedAnswer`, unchanged. |

## 6. Audience (R4)

`mayQuote(audience, requester)` (new, `toolLoop.ts`):

| `audience` | Allowed when |
|---|---|
| absent | always |
| `"admin"` | `requester?.is_admin === true` |
| `"owner"` | `requester?.is_owner === true` |
| anything else | never (the schema refuses other values anyway) |

It runs twice: on the index, to drop tools the requester could not be shown
(§2.1, so no call is spent and no restricted data reaches this machine), and
on every result, using the result's own `audience` (R4 carries it per result,
including `pending`, timeout, denial, page and replay). A result that fails
the gate reaches the model as `denied` / `not_permitted` with empty output,
and its run-record row says `withheld: true`.

The model never sees what it may not quote, so no answer, progress note or
hand-off can carry it. The prompt's audience sentence is advice on top of
that.

What "member-visible" means here: every answer posts into a chat members can
read, and the other service's own assistant answers an admin's admin-tool
question in the same chat. R4 defines the audience by the requester's flags,
and the operator's approved split (admin reads for admins) works only under
that reading. So an `"admin"` result can reach an answer to an admin, and
never an answer to a requester without `is_admin`. An anonymous admin
(`is_admin: true`, `is_owner: false` in X1 `claimed_tools_anonymous_admin.json`)
gets admin results and never owner results, which is the anonymous-admin
fail-closed rule carried over.

Nothing the install keeps is shared with members: chat conversations
(§B.14) are not implemented and the install writes no memory, so R4's
"neither enters the member-shared conversation or memory" holds by
construction. When chat conversations are built, they must store the
withheld projection, never a raw result.

## 7. Records and retention

`RelayAnswerRecord` (`answers.ts:26-53`) gains two optional fields, written
only by loop runs, so a slice 1 record keeps its bytes:

- `rounds: number`
- `toolCalls: {round, tool, page: boolean, status, code: string | null, audience: string | null, truncated: boolean, replayed: boolean, withheld: boolean, local: boolean}[]`

No `output`, no `arguments`, no `call_id`, no cursor. The input is already
recorded as received (`answers.ts:51-52`); tool outputs, including admin and
owner data, are never written under `<state>`. Retention, pruning and the
interrupted-run settlement are untouched (`answers.ts:17`, `:188-274`). The
settings view keeps showing what it shows today; listing calls there is
Deferred.

## 8. Legacy byte-identity (I5, outcome 2)

- **The claim.** `CLAIM_FEATURES` (`poller.ts:213-214`) becomes
  `["requester_context", "relay_tool_calls"]`. It is a constant because every
  target can run the loop on either engine (§1). `relay_tool_actions` is not
  listed. A service that does not list `relay_tool_calls` (theirs while the
  switch is off) sends slice 1 bytes (I5, their dark merge); nothing in the
  install branches on the descriptor's `features`, which `descriptorSchema`
  keeps ignoring (`protocol.ts:46-60`).
- **A request without callable reads** (no tools, only hand-off items, or
  `tool_guidance: null`): `answerPrompt` and `handoffAnswerSchema` /

## Deferred — not currently justified

- **Native tool exposure through MCP (option A).** Reopen if per-round CLI
  start-up proves to be the dominant latency on real traffic and both engines
  can be shown, by the probe of §B.11 test 7, to expose exactly the claimed
  tools with the credential kept out of the child.
- **Keeping one model session across rounds** (Claude `--resume`, Codex
  `exec resume`). Needs session persistence, which the one-shot profile
  forbids (`ephemeral.ts:180`, `:230`); the chat-conversation design (§B.14)
  is where sessions arrive.
- **Local validation of arguments against `parameters`.** zod 4.4.3 has
  `z.fromJSONSchema`, but any disagreement with the service's draft 2020-12
  validator would refuse valid calls; the service's `invalid_arguments` costs
  one call.
- **A persistent install-side call ledger.** §4 covers every case with ids
  that need no storage.
- **`reply_to` naming message keys returned by tool results** (their §3.12,
  outside the closed list). `checkedAnswer` keeps replacing an unknown
  `reply_to` with null.
- **Automatic page fetching.** The model decides; an automatic fetch would
  spend calls and output budget it may not need.
- **Showing tool calls in the settings view's answer detail.** The record
  holds them; nobody has asked to see them.
- **A per-relay switch for `relay_tool_calls`.** The service's switch already
  gates it, and every target supports the loop.
- **Storing the descriptor's `features`.** Nothing in the install branches on
  it.
