# Command admission, execution and outcomes

## Decision and evidence boundary

Build durable command admission for orchestration mutations. Extend the Viewer's receipt and delivery machinery with a small command-intent module and a draining executor owned by the active Viewer release. Keep the existing runtime-host, migration, deployment and delivery executors responsible for their effects. A separate gateway process is currently unjustified. First shorten the pipeline critical section around stage spawn admission and host waits; ship the common queue after that repair. These are proposed decisions, supported by the inventory and trade-offs below.

The smallest first slice is **persist stage activation, release the pipeline lease, spawn under the original identity, then reconcile into a freshly read attempt**. It targets the demonstrated cross-pipeline blocking path. Its reduction in the total number of busy refusals must be measured; neither the supplied audit nor this inspection establishes that it removes a numerical majority. Merely dropping the lease around the existing callback is unsafe: that callback mutates the controller's borrowed pipeline object and calls its borrowed `persist()` (`src/lib/pipelines/engine.ts:2956-2973`; `src/lib/state/sqliteStateStore.ts:1205-1221`).

No implementation, test, service, account or live registry was changed by this stage. Only this document was written. Proposed contracts and limits are labeled as decisions; code references describe the existing mechanism that motivates them.

## Why busy exists, and corrections to the starting hypothesis

The pipeline lease serializes read-modify-write over a collection. `SqliteStateCollection.mutate` acquires it, loads a mutable session, awaits the entire callback and releases in `finally` (`src/lib/state/sqliteStateStore.ts:1205-1221`). `tickPipelines` holds it while iterating pipelines and awaiting host reconciliation and `tickPipeline` (`src/lib/pipelines/engine.ts:4534-4576`); run-stage activation awaits spawn and occasionally handshake sleep (`:2959-3007`). An unrelated pipeline mutation must acquire the same lease (`src/lib/pipelines/store.ts:935-953`). Its bounded acquisition can therefore expire while the first operation waits on another process (`sqliteStateStore.ts:1658-1668`).

The logical collection lease and SQLite's physical writer transaction are separate. Acquiring the lease commits a row in `state_leases`; the asynchronous callback retains that logical ownership after the SQL transaction ends (`sqliteStateStore.ts:1615-1632`). Intent insertion can avoid this collection lease. It still needs a short SQLite writer transaction, disk space, fsync and authorization. Current MCP receipts already have their own SQLite database with WAL, FULL synchronization and a 5-second busy timeout (`src/lib/mcp/server.ts:1532-1558`). Reusing it without changing its blocking admission behavior would merely move some request latency.

## Current command inventory and proposed disposition

The duration column describes the actual critical-section extent and configured acquisition bounds. It is not a measured hold-time percentile. No production experiment was run to time every mutator.

Shared mechanisms:

* **P/T/F/W/B:** pipeline, task, flow, workflow and board collections in state SQLite. Each has its own logical collection lease plus short SQLite write transactions. Sync acquisition loops up to 6,000 times with 5 ms sleeps; async acquisition uses the same count and an optional wall deadline (`sqliteStateStore.ts:19-20,1640-1668`). Pipeline request admission supplies its configurable deadline (`pipelines/store.ts:918-944`); the controller uses the collection default. Sync waits can block the event loop. They are acquisition limits, never an upper bound on the callback's work.
* **A:** shared account-selection lock: process-local ownership/queue plus cross-process ticket and owner file. Sync contention in the same process refuses immediately. Async request admission defaults to 2 seconds, background admission to 10 seconds; ownership spans the entire awaited callback (`accounts/accountMutation.ts:13-22,126-146,198-205,336-360`). Nested same-context calls reuse ownership. Catalog writes also take their collection lease; registry writes take a SQL transaction (`accountMutation.ts:330-334`; `agent/registry.ts:4471-4483`).
* **J:** registry/runtime journal writes. Registry mutation begins a SQL transaction with a 5-second acquisition deadline (`agent/sqliteRegistryStore.ts:680-699`). Runtime operation admission records command/effect state within `BEGIN IMMEDIATE` (`src/runtime-host/journal.ts:719-788`). No promise held by a browser makes these writes durable.
* **R:** every mutating MCP binding first participates in its tool/request-key receipt protocol (`mcp/server.ts:93-145,2335-2336,2733-2757`). Most unfinished plain claims return `call_interrupted`; completed failures replay. Recoverable tools inspect bound downstream evidence. R is not an execution queue (`:2741-2750`; `bindings.ts:4821-4848`).
* **L:** named file transaction with process identity, queue and synchronous callback; the common implementation has 6,000 attempts at 5 ms and throws its supplied busy sentence (`state/fileTransaction.ts:7-9,168-190`). This may block a calling event loop while acquiring a lock held elsewhere.

Disposition **I** means accept a durable intent and return promptly to a client that selected the new contract. **S** means preserve an applied-result/read barrier in the existing interface, while allowing explicit intent mode where stated. **E** means reuse an existing durable executor and wrap its admission/outcomes. **H** means shorten a lock or isolate slow preparation; a general queue alone does not repair the body.

## Proposed intent and receipt contract

The following is a new contract. Existing receipt primitives are its foundation, not evidence that these fields or guarantees already exist.

Use one small module with `submit`, `read`, `cancel` and a private drain interface. Add intent and outcome-outbox tables beside existing MCP receipts in `mcp-receipts.sqlite`; expose the same module to HTTP and MCP. Keep domain effects in their existing stores. This avoids runtime-host RPC on admission and avoids the pipeline collection lease. It also makes the cross-database commit problem explicit: a domain write and a command result are reconciled by a domain application marker. They are never described as a single SQL transaction. Current receipts live in that separate database (`mcp/server.ts:3683`), while task/pipeline/registry effects use state SQLite as inventoried above.

Proposed durable record:

| Field group | Contract |
| --- | --- |

Admission transaction: validate shape and caller permission; normalize/clamp display/pagination parameters; enforce queue bounds; bind key and payload; allocate command/target IDs where safe; insert the executable intent and accepted receipt in one short transaction; commit; then schedule a drain. A crash after commit and before the scheduling signal is covered by startup recovery and watchdog enumeration. Return `accepted: true`, `commandId`, `status: queued`, receipt revision, resource sequence, result-read method and notification destination. No spawn/network/preflight wait belongs inside this transaction.

For negotiated intent mode, bypass the old claim-then-run MCP binding path and atomically write its compatibility receipt with the intent. Otherwise the old 5-second synchronous receipt wait would still precede admission. Use a dedicated connection with `busy_timeout=0`, synchronous bounded transaction bodies, and asynchronous retry outside transactions; a proposed 250 ms admission budget ends with a typed not-accepted/unknown answer as appropriate. This is a new bounded admission path, not a change to the guarantees of legacy receipt calls. CPU-heavy normalization and payload size checks finish before acquiring the writer. Recheck issuer authority and target guards at execution; permission revoked while queued refuses the still-unexecuted effect, and the executor never inherits the issuer's capability merely from payload text.

`accepted` promises durable custody, preserved identity, autonomous attempts under the stated policy, an inspectable result and a retained notification obligation. It does not promise domain validity at execution time, immediate effects, eventual success despite unavailable dependencies, delivery to a permanently unreachable recipient, or survival of permanent storage loss. Invalid schema/auth/key conflicts are refused before acceptance. Queue capacity or unavailable storage answers a typed **not accepted** response with the original key and safe retry guidance; the UI must not show it as queued. A lost admission response remains unknown until original-key lookup establishes whether the transaction committed.

Idempotency decisions:

* New intent identity is scoped by authenticated issuer, command kind and client key. Persist an index linking the existing MCP `toolName:clientRequestId` key to this identity; do not re-key historical receipts or widen access to them. Existing binding ownership checks still apply (`mcp/server.ts:2335-2336`; `mcp/bindings.ts:4825-4847`).
* Same normalized payload and identity return the same command and latest receipt. A changed semantic payload under the same key returns `idempotency_conflict`, preserving the original command. Presentation-only `compact/full`, waiting policy and lookup options do not create new effects. Keep the current numeric normalization and disclose `clamped` (`mcp/server.ts:290,2759-2760,3130-3136`). Do not silently clamp effectful priority, cancellation target or account choice.
* Persist derived downstream IDs once. Host loss, expiry of a request connection or a receipt lookup never chooses a new send/spawn key. The existing stable send derivation is the precedent (`mcp/bindings.ts:1271`; original-key tests `mcp/pipelineBusyAdmission.test.ts:104,159`).
* Reads and updates use the original command ID even after a task/pipeline is deleted. Retain unresolved commands and tombstones; age alone never evicts a key that could still execute. Default: no automatic deletion of unresolved intent/outbox rows. Completed payloads may be compacted after a published retention horizon, keeping identity/digest/result tombstones so replay cannot create a second effect.

Ordering decisions:

* FIFO by admission sequence within a pipeline, task, conversation or canonical project seat. A command touching several resources enters one transactionally allocated dependency order; sorted resource keys avoid circular acquisition. Project alias changes preserve old resource bindings through the existing canonicalization rules (`orchestrator/seats.ts:199`; project grouping contract in `AGENTS.md`).
* No global order across unrelated projects. Deployments and global account-routing choices have installation/engine keys. A task/pipeline link binds both resources. A spawn with an explicit account avoids an accidental dependency on a global selection change.
* Native conversation control precedence remains authoritative. Interrupt/cancel/kill can bypass an ordinary pending send or long-running effect only as explicit control operations against that effect's ID and generation. They cannot reorder arbitrary task edits or use a priority bit to skip prerequisites.
* A following synchronous read observes committed domain state. An accepted command does not establish read-your-write. Callers that need it await `applied`, supply `afterCommandId` to a bounded read barrier, or use the S adapter. On barrier timeout return `pending` with the same receipt. Dependent commands may use `dependsOn` instead of blocking an agent turn.

Cancellation/expiry decisions: cancellation is its own idempotent command. Queued work can atomically become cancelled with proof no dispatch began. Applying work sets `cancelRequested`; its domain executor decides whether an effect can stop. An already-completed effect returns `too_late` plus its true result. Cancellation never deletes a request or retroactively proves non-execution. Expiry is opt-in for staleness-sensitive requests and checked before dispatch; do not silently expire accepted pipeline/task edits by elapsed wall time. After dispatch, expiry starts reconciliation and may end as unknown. Controls bound to a completed/replaced turn are refused with that reason.

## Applying safely and learning the result

For a local state mutation, commit a bounded `appliedCommandId`/digest/result marker in the **same domain transaction** as the change. In the next short receipt-store transaction, settle the command and insert its outcome-outbox row. A crash between those transactions re-reads the domain marker and rebuilds the receipt/outbox without repeating the mutation. Do not retain a stale mutable task/pipeline object across a wait. The existing create-pipeline recovery lookup demonstrates the marker pattern (`mcp/bindings.ts:4825-4834`). Domain-specific adapters are required for deletes, links and multi-record operations; blanket replay of arbitrary bindings remains prohibited.

For external effects:

1. Under a short domain mutation, reserve the effect identity and expected target version. Commit before dispatch.
2. Release domain and account locks. Act through the existing domain executor using the persisted downstream key. Persist an `applying` phase before a potentially non-idempotent call.
3. Reacquire a short mutation, read the target anew and compare effect ID, attempt/generation and ownership epoch. Commit the observation only if it still belongs. A changed target creates a reconciliation obligation for the original effect; it does not authorize another spawn.
4. Read authoritative effect evidence to distinguish applied/refused/unknown. Publish the terminal result and notification obligation together in the command database.

The spawn-specific seam must change: `PipelinePorts.spawnAgent` currently takes a synchronous `onReserved` (`engine.ts:227,451-454`), invoked after registry reservation and before `spawnStructuredConversation` (`:521-578`). The first slice should make this an awaited admission callback or split reservation from actuation. Persist the command/effect plan under P, reserve in J outside P, await a fresh P transaction to bind the launch, then actuate only if that binding still authorizes it. If close/pause/retry wins before binding, retain and reconcile/cancel the reservation before launch. This accounts for the gap between creating a registry receipt and recording its ID on the attempt.

The bind transaction also records the dispatch permit/phase. That commit is the ordering point against cancellation. If cancellation wins first, no dispatch permit is granted. If dispatch wins first, close/pause records its control intent and must wait for the original effect's reconciliation before claiming teardown complete. A close cannot observe no host yet, forget the outstanding spawn, and then allow its late host to appear after terminal closure. The controller's recovery path and legacy synchronous patch path must both understand this reservation barrier in slice 1.

Applied meanings must be specific:

| Command | Applied evidence |
| --- | --- |
| Create/patch pipeline or task | Domain marker and changed revision. Pipeline creation may still be provisioning; command success says nothing about build/review success. |
| Stage report | Report recorded for the admitted attempt/turn with captured provenance. Stage verdict settlement is a separate subsequent event. |
| Spawn | Original receipt resolves to a materialized conversation/host with the initial prompt's delivery state explicitly reported. A launch ID alone is acceptance. Failure/no-progress is a pushed outcome. Unknown materialization remains visible and recoverable. |
| Send | Delivery subsystem's authoritative delivered/failed/discarded/uncertain outcome, preserving the original message key. Delivered does not prove that the recipient understood or completed the request. |
| Seat rotation | Successor activation and handoff settlement, each named; any residual predecessor cleanup reported separately. |
| Account selection/migration | Selection revision for global routing; intended-account acknowledgement for deferred reseat; actual generation/account and drained held-message result for a migration that completed. |
| Deploy | Existing coordinator terminal result plus serving/runtime-host evidence. Accepted build, promoted target and successful serving verification remain distinct phases (`runtime-host/deployment.ts:157-203`; R2). |

Pull: add `command_receipt(commandId | original kind/key)` and a bounded HTTP receipt/read endpoint. Authorization uses the original issuer or current authorized project/operator scope. Return both command outcome and notification delivery status. Existing `message_receipt`, `recoveryOnly` send/spawn reads and `deployment_status` remain valid aliases to their original evidence. Terminal evidence has precedence over an old accepted response; unreadability yields unknown, never absent/not-executed (`mcp/bindings.ts:4683-4811`; `runtime/http.ts:402-477`).

Push uses a durable outbox. One logical terminal event ID is derived from command ID and terminal receipt revision; each recipient channel has a unique acknowledgement key. Delivery attempts can repeat. Browser reducers, seat agenda items and structured-message consumers deduplicate that event ID. This supplies exactly one logical result per recipient while retaining honest transport uncertainty. There is no claim that an arbitrary external engine executes every effect exactly once.

Recipient rules (proposed):

* The ordering agent owns the direct outcome. Bind its durable conversation at admission. Deliver a short structured outcome through existing held-message/structured delivery, using an event-derived `clientMessageId`, with idle-only semantics. If its turn ended, deliver at the next admissible idle turn. If its host disappeared, use the existing reserve-before-recovery path and retain the same notification key (`structuredMessageDelivery.ts:551-613`; `structuredDeliveryQueue.recoveryContention.test.ts:326-393`). Do not inject into an unrelated generation based on a stale PID.
* An ordering manager additionally owns a project-seat agenda obligation. Resolve the current authorized successor seat when draining, preserve the original issuer in provenance, and carry the same event ID across rotation. Add command outcomes as a seat-tick source; advance its acknowledgement only after the delivery layer proves the wake landed. Existing wake settlement already follows that rule (`monitor/seatTickController.ts:873-888,928-954,1358-1373`).
* Sending both a direct manager message and a separate seat wake for the same event would duplicate work. Choose the seat channel for manager-origin commands; direct conversation delivery for other agents. A project-seat fallback may take an unreachable agent's obligation, but it remains a separately recorded escalation recipient. The original delivery stays pending/unreachable, never falsely acknowledged.
* Honor seat wake intervals and idle-only delivery. A completed command becomes visible to receipt reads/browser immediately; its manager notification is included in the next eligible wake. This is an explicit latency trade-off, based on current wake policy (`monitor/seatTick.ts:55-67,696-697`). Do not quietly turn every completion into an immediate paid agent turn.
* A permanently deleted/unauthorized conversation cannot be guaranteed delivery. Retain the outcome, route a visible obligation to the authorized project seat/operator, and show why the original recipient is unreachable. Host disappearance alone is insufficient to discard it.

Browser: project an operation row/card overlay with `Queued behind N`, `Applying`, `Waiting: <dependency>`, `Applied`, `Refused: <reason>`, `Failed: <reason and remaining effects>`, `Cancelled` or `Outcome unknown: checking`. N counts currently runnable predecessors on the same blocking resource, with its observation revision; it is not an ETA or a global queue length. Show multiple dependencies when relevant. Pending creation is visible from its reserved command/target identity before the pipeline exists. Keep the actual lane status unchanged until domain state changes. A failed review or publication cannot be disguised by a successful command acknowledgement (#1938/#1939, R5).

Publish command receipt revisions through the existing runtime event/SSE channel after writing the outbox. The current SSE implementation supports sequence replay and reset (`runtime/sse.ts:22-49`). During runtime-host failure, the browser can poll the independent command receipt endpoint; the durable outbox later republishes missing hints. On SSE reset, browser restart or an old tab reconnect, refetch outstanding command receipts. Persist pending keys across reloads; never mark a command applied from a lost spinner or elapsed timer. Browser presentation deduplication is per client; it does not consume another browser's result.

## Executor ownership, bounded work and failures

One active Viewer **scheduler owner** is the default. MCP processes and browsers submit/read only. A process-local promise, such as the current `tickStore.__llvPipelineTick` or delivery `activeDrain`, is insufficient across processes (`pipelines/engine.ts:4523-4525`; `structuredDeliveryQueue.ts:683-691`). Current hot-state authority fences releases but also admits certain unidentified local clients; it does not elect this new executor (`state/hotStateAuthority.ts:152-176`).

Proposed ownership record: release epoch/revision, process boot identity, unique acquisition token and renewable claim. Obtain it under a short receipt-store transaction **and** the existing release-activation authority. Recheck ownership in every command/domain commit. Include the acquisition/target-generation fence in external effect admission; a stale scheduler that resumes after demotion must fail before new actuation. Renew only through the active-release path. Expired heartbeat is a reason to investigate/reconcile, never enough to reissue an unknown external effect.

The external fence is required new integration: pass the active executor acquisition token through the runtime command contract and validate it against the current released/active owner when admitting an effect. Extend the existing runtime-host admission/journal seam for that check. A locally checked token followed by an unfenced RPC has a demotion race. A successor may reconcile an already-admitted effect under its original identity, while a stale owner cannot create a fresh effect. For adapters that cannot enforce this fence at the external service, reserve/record dispatch before the call and reconcile that call on takeover; do not issue it again until its outcome is proven.

Blue/green order: incumbent stops taking new execution claims, persists phases, releases only what it owns; new release activates under the existing hot-state handover, claims the executor and reconciles outstanding effects before selecting fresh work. Admission may continue through a compatible receipt writer while execution is fenced, but it must answer not accepted if no healthy admission path exists. The runtime-host keeps its existing singleton listener fence (`runtime-host/runtimeHostFence.ts:79-95,171-172`) and domain effect ownership. Add an executor bootstrap/commit gate to the existing release integration; do not infer it from a Bun process being alive.

Crash handling:

| Crash point | Recovery action |
| --- | --- |
| Before admission commit | No accepted intent. Same-key lookup, then safe resubmission only if absence is authoritative. |
| After commit, before wake signal | Startup/watchdog selects the durable queued row. |
| Claimed, before domain reservation | Validate release token and replay the idempotent reservation. |
| Reservation committed, launch ID not yet bound to pipeline | Read registry by the persisted downstream key, then CAS-bind into the original attempt before actuation. |
| Effect might have started, acknowledgement lost | Query original runtime operation/receipt/remote evidence. Keep `unknown` if unreadable. Never allocate a new key merely because a request timed out. |
| Domain change committed, command result absent | Read the atomic domain application marker; settle command and outbox. |
| Outcome delivered, delivery acknowledgement lost | Retry under the same event/message identity and reconcile recipient evidence; consumer deduplicates. |
| Poison schema or impossible transition | Quarantine this command with a typed refused/error result and notification. Continue other resources. A malformed payload cannot monopolize a global loop. |

Scheduling defaults, to be measured in isolated tests before promotion: round-robin across projects; FIFO/dependencies within each resource; at most 32 short reservations/settlements or 20 ms of local CPU per pass; at most four outstanding external effects globally and one ordinary effect per resource. Reserve one control slot so interruption/cancellation can pass an in-flight ordinary effect. Page by indexed due-state/project/resource fields and yield between pages. These numbers are proposed conservative limits, not production throughput claims.

Do not run a long external promise inside the flow/pipeline controller phase. Add a bounded command-drain wake to its lifecycle, with its own active-work bookkeeping, and signal `requestPipelineTick` only when a command's domain change requires it. The existing controller has 15-second phase deadlines, eight passes and a 30-second watchdog; timeout stops awaiting the phase but leaves its original promise active (`pipelines/controller.ts:69-72,231-255`). It does **not** cancel a held lease or authorize a duplicate tick. New execution futures must be registered, recoverable and completed outside that phase.

Back-pressure: proposed initial caps of 256 unresolved user commands per project, 4,096 globally and a separate small control allowance. Apply existing per-tool payload limits plus a total journal-byte cap. A repeated same-key call does not consume capacity. Never evict unresolved commands to make room. On capacity refusal show the counts/reason, safe same-key retry and oldest blocked resource. Fair selection uses admitted sequence with age; a noisy project cannot consume every slot. Repeated transient failures receive capped exponential retry spacing and release their execution slot. Pending storage contention is retried internally; after a declared execution policy is exhausted, issue a terminal refused result only if no effect occurred, otherwise escalate unknown reconciliation. An explicit dependency on a poison/failed command becomes a typed dependency refusal instead of waiting forever.

Observability belongs in the contract: admission latency separately from queue wait, lock-acquisition wait separately from hold time, apply/reconciliation time, oldest pending age, per-project depth, outstanding effect count, unknown count, outcome delivery lag, executor release/boot token and heartbeat. Log command kind and opaque identity plus phase/code; omit payload text and personal data. The existing controller heartbeat and runtime RPC health provide useful starting instruments (`pipelines/controller.ts:23-35`; `runtime/client.ts:19-53`). Their metrics do not currently prove command queue progress.

## Gateway verdict and over-engineering pass

| Choice | Benefits | Costs and limits |
| --- | --- | --- |
| Extend active Viewer admission/receipts | Reuses authenticated bindings, domain code and current release authority; can admit without runtime-host snapshot/RPC; simplest path to browser state and seat outcomes. | Shares Viewer event-loop/process outage. Requires bounded storage admission, a new fenced scheduler claim and reconciliation across receipt/domain databases. |
| Put the new queue in the existing runtime-host | Existing durable journal, socket and stable listener; domain message/deploy operations already live there. | R2 shows this process's requests already timing out. Every command admission would depend on it, and it would need pipeline/task/authority code or another RPC back into Viewer. This expands its outage impact. |
| Separate gateway process owning queue and HTTP/MCP admission | Can remain available while Viewer reloads or its event loop stalls; one independent admission/observation endpoint. | Adds discovery, authentication forwarding, protocol versioning, deploy/handover/rollback, health checks and another persisted ownership role. Still shares disk and domain writer/effect conflicts. A gateway's single queue does not by itself fence old Viewers or old external effects. |

**Verdict: no separate gateway now.** The requirement demands durable custody and reliable outcomes; it does not demand that admission remain available through complete Viewer process failure. R4 proves a critical-section problem; R2 shows a slow existing runtime dependency. Neither demonstrates that a third process pays for its operational cost. Revisit only after measuring admission failures attributable to Viewer unavailability after short-lock repair, and after the caller requires independent availability during a Viewer outage. If that requirement arrives, move the small admission interface/store ownership behind the gateway without duplicating domain executors.

Cut a universal event-sourcing rewrite, distributed broker, global serial worker and second message queue. A command-intent module earns its scope by hiding identity, custody, ordering and notification recovery behind one shared interface. A new framework with one adapter per existing function would spread that knowledge back across callers. Preserve existing native queues, seat intents and deployment operations.

## Migration and compatibility

Roll out server persistence/reads and executor recovery before exposing accepted-at-once behavior. Introduce an explicit versioned/negotiated `completion: accepted` mode or a new `submit_command` tool for existing agents. Old tool bindings and old browser tabs keep their applied-result contract. Adding `accepted: true` to an otherwise unchanged success object is insufficient: a client may immediately use a nonexistent task/pipeline record. For new sessions, the generated tool description can make intent mode the default only after the notification and receipt paths ship.

Create/migrate the new tables during fenced Viewer startup, with state ownership claimed before state-resolving imports. Ordinary MCP/HTTP submission may insert commands only after schema readiness; it must never opportunistically run a live-state migration. This follows `src/lib/stateOwnership.ts:15-25,60-77,270-282` and the entry-point contract in `AGENTS.md`. A schema mismatch returns a typed unavailable admission and leaves existing custody untouched.

An old adapter submits to the same module and waits for its original completion milestone. It never takes the long pipeline lease itself and never submits the operation twice. If its HTTP/MCP wait expires, preserve the command, return a typed pending/unknown response with original key and receipt lookup, and keep notification work alive. Existing mutation receipts continue replaying their historical result. Do not reinterpret an old `tool_failed`, `call_interrupted` or possibly-dispatched call as an unexecuted new intent. Recoverable send/spawn/create calls consult existing downstream evidence first (H1490; `bindings.ts:4821-4848`).

For in-flight stage reports, capture caller, attempt, turn, declared outputs and provenance while the reporting turn is still identifiable. Persist a pending-report reservation that the stage-settlement path consults before interpreting a missing report. Drain it before deciding the turn's verdict; allow replacement only within the same still-open report contract. The actor cannot silently become the executor. #1930's already-settled `needs_decision` attempt remains settled until its separately specified resolution action exists; queuing a later pass does not reopen it (R5; `engine.ts:6708-6729`).

Keep MCP answers compact and additive: original request ID, command ID, accepted/applied distinction, stable result code, target IDs/revision, bounded next action and read link. Preserve `clamped` and existing default pagination; do not return specs/prompts or whole collections. Do not turn pending work into an opaque `tool_failed`. Existing success fields that assert domain changes are populated only after those changes occur (`bindings.ts:1471-1478,1505-1514`; `server.ts:2759-2764`).

Old UI mutation paths without client keys retain their synchronous contract until updated. New UI persists a key before sending, represents pending creation/edit separately, reads receipts on reconnect, and disables only dependent actions. Unrelated work stays usable. The interface must show actual refusal reasons, not require retrying a generic busy banner.

Rollback is a protocol boundary. Install a compatible reader/drainer release before enabling new submissions. Turning admission off is safe; deleting accepted intents or downgrading to a binary that cannot drain them is unsafe. Permit binary rollback only to that compatible floor, or drain/reconcile outstanding work and explicitly preserve/export all unresolved custody first. Keep schema additions backward-readable and never erase old receipt keys. The task permits no deployment here; these are release requirements for the slices below.

## Risks, open defaults and verification limits

The hard risks are stale-object writes after lease release, an external effect succeeding before its receipt update, competing release executors, command payload/authorization drift, accepted work stranded on rollback, and notification loss during recipient rotation. The preceding protocol assigns a durable identity and reconciliation path to each; future isolated tests must prove them. In particular, extending a receipt store and adding a timer alone fails this design.

The complete lock-hold distribution, the causal owner of each production refusal, and the two reported direct-spawn incidents were not re-established from raw production logs/SQLite in this stage. R2–R4 are bounded read evidence; they do not support a percentage improvement claim. Account lifecycle and peripheral provider call duration are source/tracker inventory, not timed experiments. No new external API behavior was assumed: existing adapters remain the authority; unknown delivery is exposed as such.

Open choices are resolved to defaults rather than blocking this document: Viewer-owned admission/execution; separate command tables beside MCP receipts; FIFO per resource with fair project scheduling; optional accepted-mode migration; no automatic expiry of ordinary orchestration writes; manager outcomes through eligible seat wakes; explicit unknown state for unreconciled effects. Proposed batch/cap numbers need isolated load validation. The gateway decision is reversible at the admission interface; no separate ADR is necessary for this read-only proposal. Enabling durable custody and setting the minimum rollback-compatible release require a release decision when implemented.

### Deferred — not currently justified

* A separately deployed gateway, broker or distributed scheduler. Reconsider with measured independent-availability requirements.
* Converting every media/configuration/login exchange into an asynchronous intent. Preserve the synchronous result contracts listed above.
* A global FIFO that waits for external effects, blanket retries of uncertain operations, and blanket exactly-once execution claims.
* Replacing native message queues, seat intents, deployment coordination or account migration with a second engine.
* Solving #1930 decision reopening, #1938 review-budget semantics or #1939 publication reconciliation by changing the queue's meaning of success. Those need their own domain fixes; the command receipt must report their actual outcomes.
* Releasing startup admission while its callbacks still mutate borrowed state. First establish equivalent effect reservations and release fencing (`pipelines/store.ts:956-974`; `runtime/startup.ts:1179`).

Validation against the originating requirement: an opted-in agent hands over a durable command, receives its identity promptly and continues working; the system drains it without caller retries caused by a pipeline collection lease; pull remains authoritative and push remains owed until acknowledged or visibly escalated. Invalid, stale, unauthorized, capacity-exceeding and unprovable effects keep explicit outcomes. Slice 1 removes the known long hold, while slices 3–6 establish the complete acceptance/execution/notification contract. The requirement is served without adding a separate gateway process.


## Slice 1 implementation and compatibility

Run-stage activation has an opt-in drain, enabled by `LLV_PIPELINE_ACTIVATION_DRAIN=1`.
The default remains the legacy path until the feature is enabled. Each activation
stores its immutable spawn input, downstream key, attempt identity and control/graph
fence under the collection lease. The executor claims it with a PID, process start
identity and boot epoch, then performs account admission and structured spawn outside
the lease. The adapter awaits a new transaction binding the registry reservation and
granting dispatch. Every checkpoint and completion reads the current attempt again.

Cancellation before that permit prevents actuation. Pause preserves its control state
when an already-permitted launch finishes. Close keeps a durable teardown obligation
and cannot report terminal closure while the original launch is outstanding. A graph
edit invalidates admission under the old graph. Retry and skip cannot discard an
outstanding activation. Changes to unrelated pipelines remain admissible during the
account and runtime waits.

Recovery uses positive process-death evidence; an elapsed lease or unreadable process
identity cannot transfer execution ownership. A living process can recover its own
abandoned claim after its previous drain has exited. An interrupted pre-bind call
reuses its stored downstream key to retrieve the original registry reservation. The
existing adapter never actuates a replay: an unresolved recovered reservation parks
for receipt reconciliation. This deliberately chooses the interpretation that cannot
double-launch. After a dispatch permit, recovery reads the original receipt without
calling spawn again. A settled checkpoint retains the established transient retry
budget, retired launch list and next due time across a crash.

Disabling the flag stops new reservations. Existing records continue through the same
drainer until reconciled, including close obligations. Binary rollback must retain
this reader/drainer floor until no activation or activation-close record remains;
turning the flag off does not authorize an older binary to bypass unresolved custody.

The existing staged-launch recovery and publication protocols retain their ownership.
This slice does not move host teardown, provisioning reconciliation, embedded review
flows or every other awaited port out of the collection lease. Those remaining waits
are the separately scoped slice 1a above.


### Slice 1 isolated measurements

The existing engine test runs the same held-spawn workload with the feature disabled
and enabled. It holds the fake spawn for 100 ms, attempts an unrelated create and
retry-stage with a 20 ms admission bound, reads the lease table while waiting, and
measures each collection-lease acquisition/release interval. One recorded run measured
**161.3 ms maximum with the feature disabled** and **7.0 ms enabled**. Both commands
refused with busy in the disabled control and committed while spawn remained pending
in the enabled case. These are local controlled measurements, with no production
percentage claim. Separate coverage drives the real structured-spawn adapter through
fake account and runtime waits and checks the lease is absent at both boundaries.

Crash and race cases include two processes contending for one activation, process
exit after registry reservation before binding, cancellation before the permit,
pause/close after the permit, a failed final reacquisition, settled retry/staged
checkpoints, and uncertain read-write first-message reconciliation. The tests use
private state/config/provider homes; no live registry or host is involved.
