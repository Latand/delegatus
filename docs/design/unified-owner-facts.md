# Read one conversation, retire one attempt root, judge one check

On 20 November 2026 the requester asked for one implementation of three changes. Opening the designated conversation must work independently of board construction. Ending work must schedule the temporary directories it created. A stage, a push and a batch merger must agree on the work required to verify a candidate and use the same verified result wherever their inputs and authority agree. The public requirements are #4280, #4281 and #4282. The design was first written against main at `50e53c0031` (20 November 2026) and re-checked on 22 November against `7bc9b9de0`. It was re-checked again on 24 November 2026 against main at `43fab846a`: every file, symbol, line and behaviour it cites was read again, the 36 commits between the two bases are accounted for in the Status section below, and the open pull request that overlaps phase 1 (#4371) was read from its diff. #4372 has since merged and closed #4281. A second review on 24 November found eight more defects against the same base, and a third found seven; each is corrected in place below and listed under Review dispositions. A fourth review found one more P1 and four P2. This is the final design revision: main at `b0de5fb1e` (#4376, merged 24 November) is merged into this branch, every site in the phases was read again on it, and the detail each phase lane must carry as acceptance is collected under "Open items for implementation". Line numbers in the phases describe `b0de5fb1e` and drift; the symbol is the stable handle. Line numbers inside a review disposition describe the main of that review's round.

## Decision

Record each fact where its owner can first establish it. Give consumers a keyed read and make the consumer of an irreversible effect check that the fact is still current. A deadline nominates a root for inspection. A passing test nominates a particular check for reuse. Neither fact grants permission to act on a changed subject.

| Module and owner | Interface at the seam | Implementation and adapters | Depth, leverage and locality |
| --- | --- | --- | --- |
| Conversation identity, owned by the agent registry | Resolve an ID or former path to one currently readable entry | Indexed generations, aliases, path ownership and materialization, followed by one scanner metadata read. The desktop dock and the phone use the same HTTP adapter. | Panels can bind a conversation whose row has never appeared on their board. A change in generation resolution has one implementation. |
| Attempt retention, owned jointly by the root allocator for identity and the attempt/lane or standalone host for lifetime | Register and release a root, observe an owner transition, take due roots | The existing attempt SQLite inventory and leased retention helper. Pipeline and standalone registry adapters supply different terminal proofs. | A close or reopen reaches both scratch and config roots. One removal implementation still protects every producer. |
| Local verification, owned by the gate runner | Plan a subject, satisfy a check, read its verified outcome | The existing planner, bounded receipt store, owned runner and broker. Stage CLI, Git hook and batch runner are adapters. | Changing which test exercises publication or what invalidates its result has one place to change. |

**There is no shared storage or execution seam across these three modules.** Conversation identity survives indefinitely, scratch ownership ends after physical retirement, and check evidence expires or becomes inapplicable with its inputs. A common fact table, event bus or invalidation service would add a fourth lifetime. The common design is the ownership rule.

## Candidates explored

Following a single click, a single release and a single compiler start exposed three places where a caller must understand several modules to use one fact. The seat resolver requires an entire catalog as its argument. The release callback has a pathname and cannot express which allocation ended. The planner returns commands, so a second adapter has to decide again whether a completed command satisfies its obligation. Unit tests can pass at each of those interfaces while the user still waits, a root remains undiscovered, or a second compiler starts.

### Top recommendation

Land the conversation reader first. A cold open with the board queue blocked falsifies its contract in one user action, and the board reader remains available throughout the switch. Next land the lifetime writes before replacing selection so a missed event cannot strand a root. Migrate the gate consumers last, starting with the planner and ending at the batch publication boundary.

Accept a registered former path in path mode. The normal seat request uses only its durable ID. ### Manager authority by identity

`authorizedManagerSeats` (`orchestrator/authority.ts:88–117`) takes `activeSeats()` and `revocations()` as sources. Its production callers supply the normalized seat file: `orchestratorWorkspacePrincipalsOrUnknown` (`orchestrator/seats.ts:1079–1090`) reads `readOrchestratorSeatStore(["slots", "revocations"])` and passes `file.seats`. That map holds only the **current slot winner of each canonical project**: `normalizeOrchestratorSeatDocument` (`orchestrator/seatRecords.ts:289–305`) canonicalizes each stored `seat:<project>` row's project key through the alias resolver (`:302`) and keeps it only if its epoch is strictly higher than the slot already kept for that canonical project (`retainNewestSeat`, `:265–268`). The rows reach the normalizer in the order the seat store selects them, `ORDER BY row_order, row_key` within the collection (`state/sqliteStateStore.ts:1930–1933`, through `selectParts`, `orchestrator/seatStore.ts:392`), so an equal epoch keeps the earlier row. The rule then has two fail-closed clauses. A conversation named by current slots in two different projects gets no authority. A revocation at an epoch at or above the seat's epoch ends it, including a revocation written under a former conversation ID that now aliases the canonical one. A cold read that called the helper on the full sources would traverse every seat row and revocation row, so its cost would grow with unrelated seat history. A read that looked only at the project slot would miss a duplicate claim in another project or a revocation under a former ID. A read that looked only at raw rows naming the conversation would see a **displaced** slot: a row for conversation A stored under a former project key, outranked by a newer row for conversation B under the canonical key, is absent from the full helper's input but present in a conversation index. Phase 1 adds an owner-backed keyed read to the seat store that reproduces the normalized input for the conversation it asks about, and keeps one implementation of the rule:

* **Stored shape.** The seat store does not write the seat or revocation object as the row's JSON. `recordRows` (`orchestrator/seatStore.ts:286–316`) produces the value per key, and both the import (`importRows`, `:323–326`) and every later write (the `SeatRow` records at `:850–857`) store the envelope `{key, value}` (`rowJson`, `:318–320`); the reader unwraps `parsed.value` only when `parsed.key` equals the row key (`decodeStored`, `:374–382`). The conversation ID of a slot or a revocation is therefore at `$.value.conversationId`, and `$.conversationId` is NULL on every production row.
* **Stored texts.** A slot value is not the seat either. `storedSeat` (`seatStore.ts:235–243`) replaces `mandate` with `mandateText` and an optional `roleTable` with `roleTableText`, the SHA-256 digests of rows `text:<digest>` (`TEXT_PREFIX`, `:99`, written by `recordRows` at `:314`). The full reader puts the texts back before it normalizes: `loadTexts` (`:483–504`) reads the digests every loaded slot names by exact key, `snapshotDocument` (`:543–546`) passes each slot value through `hydratedSeat` (`:247–256`), and only then does `normalizeOrchestratorSeatDocument` call `normalizeSeat`, which drops a row without a string `mandate` (`seatRecords.ts:220`). Passing a stored row to `normalizeSeat` directly would drop every production-written slot. When a named text is absent, `hydratedSeat` returns the row without its mandate (`:252`, `:255`), so the normalizer drops that row as torn. `loadTexts` reports such a miss at the snapshot's own revision as loaded (`:502–503`), so the row is dropped and another row can win the slot; a miss read at a different revision is stale (`:503`), and `readOrchestratorSeatStore` retries (`:685–687`) and answers unknown after three attempts (`:694`).
* **Index.** Additive partial expression indexes on `state_rows` for the collection `orchestrator_seats` (`ORCHESTRATOR_SEAT_COLLECTION`, `seatStore.ts:93`), in the form of `state_rows_task_project` (`sqliteStateStore.ts:709–711`): `ON state_rows(json_extract(value_json,'$.value.conversationId'), row_key) WHERE collection='orchestrator_seats' AND substr(row_key,1,5)='seat:' AND json_valid(value_json)` for slots, and the same expression with `substr(row_key,1,11)='revocation:'` for revocations (the prefixes are `SLOT_PREFIX.seats` and `SEQUENCE_PREFIX.revocations`, `seatStore.ts:100–101`). The reading statements repeat the indexed expression and the partial predicate verbatim so the planner can use them, and the reader accepts a row only after `decodeStored` has validated its envelope key. They use `json_extract` only, so they compile on SQLite 3.39, and they build from existing rows with `CREATE INDEX IF NOT EXISTS` under the startup mutation fence, so no table, trigger or backfill is added. Slot rows are already addressable by exact key. A reader that finds an index absent returns retryable unavailability and withholds any partial answer. Before the seat store has been imported into SQLite (the legacy file path in `readOrchestratorSeatStore`, `seatStore.ts:699–701`) there is no index; the keyed read answers from the existing revision-cached full map.
* **Read, conversation direction.** `seatClaimsByConversation(ids)` takes the canonical ID and every former ID that resolves to it. The former IDs come from the registry's alias lookup index (`registry_lookup_alias`, created at `sqliteRegistryStore.ts:424`), probed once per hop of the chain within one synchronous `withConversationAliases` generation; the chain is bounded and a cycle fails closed. In one read transaction at one collection revision, and under one project alias snapshot, the read:
  1. finds the `seat:` rows that name any of those IDs and the `revocation:` rows that name any of them, by index range;
  2. for each candidate seat row, validates its envelope with `decodeStored`, hydrates its texts (below), normalizes it with the existing `normalizeSeat` and active-slot predicate (a row whose stored project differs from its key, or that is not active with a conversation, is dropped as the full reader drops it) and computes its canonical project;
  3. reads that canonical project's **current slot**: the exact `seat:<key>` rows for every raw key that resolves to it (`projectAliasKeys` over the decision's pinned alias snapshot, as changed under "Pinned alias snapshot" above), each decoded, hydrated and normalized the same way, then ranked by `retainNewestSeat` in `row_order, row_key` order;
  4. keeps the candidate as a claim only when it is that winner, with the same row key, conversation and epoch.

  **Hydration in the same read.** For the candidate rows of step 2 and every slot contender of step 3, the read collects the `mandateText` and `roleTableText` digests, takes each one from the process text cache when it holds it (texts are content-addressed, so `loadTexts` does the same at `seatStore.ts:492`), reads the rest as exact `text:<digest>` keys in the same read transaction and at the same collection revision, and passes each value through the existing `hydratedSeat` unchanged. A text that is absent at that revision gives `hydratedSeat`'s result without a mandate, so `normalizeSeat` drops that contender, exactly as the full reader drops it on a same-revision miss, and the next contender by epoch and row order can win. One transaction has one revision, so the full reader's stale-text retry has no counterpart here. A text read that fails returns retryable unavailability and no partial answer, as the full reader answers unknown. Texts are needed only to reproduce the normalizer's acceptance; the claim carries no mandate. The project direction and the binding read use the same step.

**Attempt clock.** This is `attemptScratchExpiry` (`attemptScratchPolicy.ts:14–37`) as it stands on main; phase 2 changes none of its clauses. For a root whose launch has `retainUntilClose = false`, the scratch deadline is the terminal attempt's authoritative completion time (`completedAt` of a `passed`, `failed` or `skipped` attempt; a retired launch uses its `retiredAt`) plus 24 hours plus one millisecond, `ATTEMPT_SCRATCH_EXPIRY_OFFSET_MS` (`:7`). The completion time must be a finite instant not earlier than the root's creation time (`:33–34`). An attempt clock that fails this test (no completion time, an unparseable one, one earlier than the root's creation, or a retired launch whose `retiredAt` is absent or unparseable) yields no attempt deadline, and the predicate **falls through to the lane clock** (`:36`). On a closed or completed lane that `laneFinish` (`pipelines/laneFinish.ts:30–49`) has finished, the root then gets the lane deadline `finish.expiresAt`, the latest authoritative terminal time plus 24 hours plus one millisecond. On an open lane, or a terminal lane `laneFinish` has not finished, it stays held and the audit revisits it. `laneFinish` reads `closedAt`, every attempt's `completedAt` (through `attemptEndKnown`, `:23–26`, and `latestTerminalTime`, `:7–13`), the release journal and the merge time, and never reads `retiredAt`, so an unusable `retiredAt` on a closed lane with a valid finish still yields that lane deadline. The deadline nominates the root for inspection and grants no permission to remove it. The predicate evaluates, at the current owner revision and in this order:

* a closed or completed lane whose finish `laneFinish` has not established holds the root (`:15–17`);
* a running, spawning, activated or unresolved-termination attempt holds it (`:20`);
* on an **open** lane, a **passed** attempt that is the newest attempt of the stage the cursor points at holds it (`:21–26`). A comparison takeover can reactivate the cursor on an already passed attempt, so the cursor retains it until it advances. A **failed** or skipped attempt on that cursor is not held: a parked failure leaves the cursor pending after the attempt is terminal, and its roots receive their completion-time deadline while the lane stays parked. A path that reactivates a failed attempt in place makes it running or activated, which the previous clause holds again;
* without `retainUntilClose` and without a lane-level hold that names scratch (a requested activation close, unconfirmed hosts or a pending remote action, `:27–28`), the attempt clock applies (`:29–34`) when its completion time is valid, and an invalid one falls through to the next clause;
* otherwise the root follows the lane clock, which exists only once the lane is closed or completed and finished (`:36`). On an open lane under a lane-level hold it stays held until the hold clears, and the attempt clock then applies again.

A root with `retainUntilClose = true` follows the lane clock (`laneFinish`), because its owner asked to keep it until close. Live consumers are not a scheduling input. **Continuity through execution.** Two equal content digests prove that the bytes were the same at two instants. They leave open which bytes the checker read between them. Today `stepPasses` (`local-gate.ts:726–763`) takes `initial = snapshot()` once and `passed(step)` seals when a second `snapshot()` has the same key. The green-file seal added by #4348 (`sameHeadInputs`, `local-gate-tests.ts:620–640`) compares the same kind of endpoints around one file's run. Both snapshots hash the working tree and the installed tree by content (`workingInputsFingerprint` and `installedFingerprint`, `gate-cache.ts:58–68`). A source file that holds a type error in the committed tree can be replaced by a clean version after the first snapshot, read in that form by the compiler and restored before the second snapshot. Both snapshots match, and a linked checkout can then reuse a green pass for a tree the compiler never read. The same edit also publishes the tree on the **first** run, with no reusable pass involved. File metadata cannot close this gap either. The third review on 24 November observed, on one device, that an ordinary write advanced `ctime` in a scratch probe, and that on the same device a byte changed and restored through an already writable shared mapping was read back by an ordinary read while all six metadata fields (`dev`, `ino`, `size`, `mode`, `mtime`, `ctime`) stayed equal before and after. A stat recheck around the run, with or without a `ctime` probe, therefore passes the edit, read and restore case it is meant to refuse. The earlier revision of this design relied on that recheck and is withdrawn. A check proves its inputs only when the checker cannot read anything other than the subject:

* **Immutable input view.** Every step of a plan executes in an input view, a directory the gate owns, which holds exactly the subject's bytes and which no path in the lane checkout reaches. The gate materializes it before dispatch. For a committed subject (pre-push, publication preparation, batch) it writes each file from the Git objects of the subject tree, so the content is fixed by the tree ID the plan names and no working-tree read takes part. For a working-tree subject (a stage `check-step` with uncommitted changes) it copies the working inputs as `createRuntimeCheckTree` already does for runtime checks (`local-gate.ts:284–303`, from `git ls-files --cached --others --exclude-standard`), with links dereferenced under the confinement rule below and then hashes the **copies**; the subject digest is the digest of what the view holds, so a concurrent edit in the checkout can at worst produce a subject that differs from the publication's, which is a miss. Declared ignored inputs that `tsconfig.json` includes (`tsconfig.json:31–40`: `next-env.d.ts`, `.next/types`, `.next/dev/types`, `.next/dev/dev/types`) are copied into the view by content and hashed there in the same way. Input files and directories in the view are read-only. The only writable entries are the declared outputs of the step: the compiler's `tsconfig.tsbuildinfo` and the build directories `createRuntimeCheckTree` already treats as generated (`node_modules`, `.next`, `dist`, `local-gate.ts:286`), and each step's state, HOME and temporary roots, which `isolatedEnvironment` already places outside the tree.
* **Private dependency tree.** Today `createRuntimeCheckTree` links the view's `node_modules` to the checkout's own (`local-gate.ts:297`), which a dependency edit in the checkout would reach. The view instead links a dependency tree the gate installs itself with `bun install --frozen-lockfile` from the subject's lockfile, with a copying install backend, so no file in it shares an inode with the checkout or with the shared package cache. It lives under the repository's Git common directory beside the existing gate cache (`cacheDirectory`, `gate-cache.ts:70–73`), keyed by the digest of the lockfile, every workspace `package.json`, the tracked `patches/`, `bunfig.toml`, the Bun pin, the platform and the architecture, and is shared read-only by every view of that repository with the same key. A running check holds a shared claim on its key; eviction keeps any claimed key and otherwise the most recent two, and the existing install step's frozen-lockfile check keeps its meaning. The installed fingerprint in the key is that tree's.
* **Confinement of resolved inputs.** Every path a step can open must resolve, after following links, inside the view or inside the sealed dependency tree; a link is an input like any other and cannot point back into the lane checkout. Today's copy precedent preserves links as links (`cpSync(..., { verbatimSymlinks: true })`, `local-gate.ts:295`), so a copied `next-env.d.ts` or `.next/types` entry that is a link would still resolve into the checkout, and the compiler would read the checkout's current bytes through it. The view applies four rules:
  1. **Copied inputs are copied by content.** Declared ignored inputs and the working inputs of a working-tree subject are read with links followed and written into the view as regular files; the copy is what is hashed and what the step reads. A source whose resolved path lies outside the checkout's work tree, or that is not a regular file or directory after resolution, refuses the run as **inputs unverified** with the path as its reason. No `verbatimSymlinks` copy takes part.
  2. **Tracked links stay inside the view.** A tracked link (mode `120000`; the tree at `b0de5fb1e` has none) is written from its blob as a link only when its target, resolved from its own directory in the view, stays inside the view root; any other target refuses as inputs unverified.
  3. **The dependency tree is confined once, at install.** After the copying install the gate walks the new tree once, requires every link in it (the `.bin` entries, for example) to resolve inside the tree, and refuses `link:`, `file:` and `portal:` dependencies and any workspace link that resolves outside it (`bun.lock` at `b0de5fb1e` declares only the root workspace and none of these). The walk's manifest digest is sealed with the dependency key and the tree is made read-only; it is not walked again per run. The view's own `node_modules` link to that tree is the only link the view holds besides confined tracked links. Bun and TypeScript (`preserveSymlinks` unset in `tsconfig.json`) resolve through that link to real paths inside the sealed tree.
  4. **The manifest records entry type and link target.** The view manifest holds each entry's type and, for a link, its target text, so the view check below detects a link added, retargeted or replaced by a file.
  The linked-input regression that proves these rules is open item 5.1.
* **Git context in the view.** Git-aware steps need a work tree, HEAD, a base, configuration and the gate caches: ESLint resolves the Git common directory for its cache (`scripts/eslint-changes.ts:47,57`), the touched comparator resolves the base and HEAD (`scripts/local-gate-tests.ts:597–598`), lists the base tree (`:650`), reads `remote.origin.url` (`:654`) and clones the repository for its baseline (`:668–669`), and every gate cache family resolves through `cacheDirectory` (`gate-cache.ts:70–73`). A directory holding only tree files answers `fatal: not a git repository` to all of them. The view therefore carries its own Git directory, written by the gate beside the view and outside the lane checkout:
  * The view root holds a `.git` file whose `gitdir:` names that private directory. Its `objects/info/alternates` names the repository's object directory, which supplies the subject and base objects by content-addressed ID; objects are never resolved from the checkout's work tree.
  * `HEAD` is detached at the subject commit (for a working-tree subject, the checkout's HEAD commit read at materialization, with the copied files as the working tree, as main's comparator already treats the head sample). The private index is written from the subject (the subject tree, or the copied working inputs), so `status`, `ls-files` and `diff` describe the view.
  * The base is passed to each step as the planner's resolved commit ID and is also written as one private ref, `refs/delegatus/base`; no step resolves a ref name against the checkout or the common directory's refs.
  * Configuration is a private `config` file holding the values of the keys the steps read (`remote.origin.url`, and the `core.*` keys that change file content or names, such as `core.autocrlf`, `core.symlinks` and `core.ignoreCase`), copied once at materialization and hashed into the subject key. Global and system configuration are excluded by the isolated HOME and `GIT_CONFIG_NOSYSTEM=1`. `GIT_CEILING_DIRECTORIES` names the view's parent so discovery cannot climb out, and the environment keeps `isolatedEnvironment`'s removal of `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_COMMON_DIR`, `GIT_OBJECT_DIRECTORY` and the other hook-exported keys (`local-gate.ts:246–253`).
  * The gate caches stay where they are today: the requesting repository's common directory is resolved before the view is created (as "Local trust and receipt ownership" requires) and passed to each step explicitly, so `cacheDirectory`, the head-file and baseline caches and the ESLint cache never derive their location from the view's private Git directory or from the checkout's work tree.
  * The comparator's `git clone --shared` for its baseline clones from the view's private Git directory, which reaches the base objects through its alternates.
  The view check below also confirms that the private `HEAD`, index, refs and `config` equal what materialization wrote. The hook case that reaches ESLint and the touched comparator in the view while the checkout's HEAD, configuration and base ref change is open item 5.2.
* **Persistent per checkout.** A fresh view per run would discard the compiler's incremental state, so the view is kept per executing checkout and per gate implementation version, and synchronized before each run: the gate records the tree ID and a manifest (path, blob ID, mode, inode, size, `mtime`, `ctime`) of what it last materialized, rewrites only the paths whose blob changed between that tree and the subject (`git diff-tree -r --raw`), removes deleted paths, and rewrites any path whose manifest metadata no longer matches. `tsconfig.tsbuildinfo` stays in the view between runs, so a second push after a one-file edit compiles incrementally. One writer claim per view, taken in the same ordered acquisition as the execution claims before heavy admission and released after cleanup, serializes runs that share a view. A linked batch worktree has its own view, so it keeps its own incremental output. The remote gate runner already meets the same rule by reproducing the exact tree ID from a bundle before it starts anything (`docs/design/remote-gate-runner.md`).
* **What the view proves.** The verdict binds the subject's tree ID (or the digest of the copied working inputs), the view's Git context and the dependency key, and holds for exactly those bytes, whatever happens in the lane checkout during the run, by any write path, a shared mapping or a link target included, because no path the step can resolve leads there. A process that deliberately addresses the gate's private view or dependency tree is a writer to the shared cache, which "Local trust and receipt ownership" below already places outside what local verification defends against.
* **View check, a guard.** After the process tree is reaped and cleanup is confirmed, and before both the caller's verdict and the seal, the gate compares the view's input manifest by `lstat` (entry type and link target included), confirms the private Git directory's `HEAD`, index, refs and `config`, and confirms that the view root and the sealed dependency tree keep their identity. This catches a step or a gate defect that wrote into its own inputs; it is a guard and proves nothing about a deliberate writer. Any difference, a failed materialization or sync, a dependency install that did not complete, or a subject digest that differs from the plan's, gives the run the distinct outcome **inputs unverified**.
* **Inputs unverified is its own result, settled first.** It is decided before the exit code and before any diagnostic classification, so exit 0 and a non-zero exit are refused the same way. `settle` (`local-gate.ts:835–837`) and the group's settlement (`:893`, `:898`) check it first and throw a decisive refusal, `inputs unverified: <step> (<reason>)`, before `passed(step)` or `passed(member)`, so a single step never reaches `:869` and publication preparation never reaches `writePublicationCheckReceipt` (`:1344–1346`); the native hook then has no receipt to admit a push. In batch, `gateCommand` (`merge-batch.ts:720`) returns the outcome beside its exit code, and `gate` checks it immediately after `:1184`, before `if (!result.code) continue` (`:1185`) and before `gateCannotRun` (`:1186`): it throws `<gate> inputs unverified (<reason>); batch not gated`. Without that order a TypeScript exit 1 or 2 with a `TS` diagnostic passes `gateCannotRun`'s test (`:380–382`) as attributable, and a lint refusal is never cannot-run, so either would reach `culprit` (`:1187–1188`) and `revalidate`/`rebuild` (`:1192–1193`) on evidence of no value. The throw leaves membership and row statuses unchanged, writes no `state.gated` (`:1199`) and pushes no tip. The step's full output, its compiler diagnostics included, stays in its log under the retained gate sandbox, headed as unverified. There is no in-process rerun: the publication's existing refusal handling (the timed retries of an unchanged head, or the producer repair turn, `docs/design/publication-producer-repair.md`) and the stage or batch caller's own retry run the check again in a freshly synchronized view.
* **Producer seal and caller verdict share the run.** The view check runs once, after cleanup and before both the caller's verdict and the seal, so a run cannot pass its caller and then fail its seal, or the reverse.
* **One helper.** The whole-step pass, the portable compiler hit and the green-file seal run in the same view helper, so stage, hook and batch get the same input binding from one implementation. The corpus overlays the batch writes for bisection today (`merge-batch.ts:749–754`, restored at `:765–770`) are written into the view as declared subject inputs and hashed there.
* **Cost.** Synchronization costs one `diff-tree` and one `lstat` per view entry, plus writes of changed blobs; the dependency tree costs one install and one confinement walk per dependency key per repository; the private Git directory costs one index write per synchronization. A view whose upkeep spends more than it saves fails the comparison.

## Deferred — not currently justified

**Attention indexes and compiler exports.** The bounded attention sources already support the designated seat through the shared overlays. A second persisted representation would add catch-up and failure modes to every writer. The board's batch implementation already serves its own consumers. A fresh export for every types miss would discard a lane's warm compiler state on the next push, so phase 5 keeps one persistent input view per executing checkout and synchronizes it incrementally. These cuts are reflected in phases 1 and 5.

**Engine split and behavioral selection.** The design considered moving 4,007 lines into launch, settlement and publication modules, keeping shared controller changes on full coverage. The review replayed every zero-context engine hunk on parent and child across the 42 first-parent commits from `git log --first-parent --since=2026-11-06T10:25Z --until=2026-11-20T10:25Z --format=%H 50e53c0031 -- src/lib/pipelines/engine.ts`. Two commits (`97d224fbfe`, `4fe10c6a11`) localized to launch and one (`2451da7daa`) to settlement. Four also changed imports or declarations absent at the base, and 35 touched the shared facade. The frozen inventory has 26 launch, 43 settlement, five publication and 16 transition files. Including required secondary owners gives selections of 90, 90 and 64 respectively. No commit localized to publication. **Zero of 42** would get a smaller set under this cut. The replay was not extended past that window: one later commit (#4196) also changes `engine.ts`, and the tracked `engine.*.test.ts` family has grown from 90 files at `7bc9b9de0` to 97 at `43fab846a` and `b0de5fb1e`. Counts describe selection and make no CPU claim. A future proposal would need to demonstrate a smaller safe selection on actual changes around patching, admission, port wiring or run-stage ticks before moving those declarations.

**Local forgery resistance.** A writer with control of the shared checkout and cache can fabricate local evidence or replace its hook. A checksum detects corruption and does not authenticate that writer. Protecting against such a writer would also require trusted publication entry points outside the checkout. The requirement permits local reuse when the implementations share trust. Separate verification identities, a privileged installation, protected storage and forgery fixtures would serve a different requirement and are deferred.

General-purpose event sourcing, a new conversation database, redesigning the board cache or search, deletion based on directory names or age, changing Docker retention policy, remote sharing of arbitrary test receipts, a replacement broker, and a repository-wide rewrite of the pipeline engine fall outside this request. Each chosen change has a concrete consumer and a measurable deletion.
