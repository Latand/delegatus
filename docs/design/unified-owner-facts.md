# Read one conversation, retire one attempt root, judge one check

On 20 November 2026 the requester asked for one implementation of three changes. Opening the designated conversation must work independently of board construction. Ending work must schedule the temporary directories it created. A stage, a push and a batch merger must agree on the work required to verify a candidate and use the same verified result wherever their inputs and authority agree. The public requirements are #4280, #4281 and #4282. This design uses main at `50e53c0031`.

## Decision

Record each fact where its owner can first establish it. Give consumers a keyed read and make the consumer of an irreversible effect check that the fact is still current. A deadline nominates a root for inspection. A passing test nominates a particular check for reuse. Neither fact grants permission to act on a changed subject.

| Module and owner | Interface at the seam | Implementation and adapters | Depth, leverage and locality |
| --- | --- | --- | --- |
| Conversation identity, owned by the agent registry | Resolve an ID or former path to one currently readable entry | Indexed generations, aliases, path ownership and materialization, followed by one scanner metadata read. The desktop dock and the phone use the same HTTP adapter. | Panels can bind a conversation whose row has never appeared on their board. A change in generation resolution has one implementation. |
| Attempt retention, owned jointly by the root allocator for identity and the attempt/lane or standalone host for lifetime | Register and release a root, observe an owner transition, take due roots | The existing attempt SQLite inventory and leased retention helper. Pipeline and standalone registry adapters supply different terminal proofs. | A close or reopen reaches both scratch and config roots. One removal implementation still protects every producer. |
| Local verification, owned by the gate runner | Plan a subject, satisfy a check, read its verified outcome | The existing planner, bounded receipt store, owned runner and broker. Stage CLI, Git hook and batch runner are adapters. | Changing which test exercises publication or what invalidates its result has one place to change. |

**There is no shared storage or execution seam across these three modules.** Conversation identity survives indefinitely, scratch ownership ends after physical retirement, and check evidence expires or becomes inapplicable with its inputs. A common fact table, event bus or invalidation service would add a fourth lifetime. The common design is the ownership rule.

## Candidates explored

Following a single click, a single release and a single compiler start exposed three places where a caller must understand several modules to use one fact. The seat resolver requires an entire catalog as its argument. The release callback has a pathname and cannot express which allocation ended. The planner returns commands, so a second adapter has to decide again whether a completed command satisfies its obligation. Unit tests can pass at each of those interfaces while the user still waits, a root remains undiscovered, or a second compiler starts.

The arrows trace one operation before and after each proposed change. The deletion test asks whether removing code concentrates responsibility or merely moves the same work to another caller.

### Top recommendation

Land the conversation reader first. A cold open with the board queue blocked falsifies its contract in one user action, and the board reader remains available throughout the switch. Next land the lifetime writes before replacing selection so a missed event cannot strand a root. Migrate the gate consumers last, starting with the planner and ending at the batch publication boundary.

### What the seat reads

At the design base, `seatState.ts:675` calls `attentionId(input.file, now)`. The dock and phone card/sheet share that state. The phone also reads context percentage and hands the entry to its focus pane. `OrchestratorConversation` passes the row to the feed, host controls, dead-host banner and composer. `useSeatSurface` and the pane call the capability resolver with both row and live session. A metadata-only row silently removes an open bridge decision from all these seat views.

Use a single server implementation, `projectConversationEntry(target, sources, now)`. The board adapter supplies its already loaded maps and batch clock. The entry adapter supplies keyed observations after authorization. Both apply identical title, activity and attention rules. Keep board-wide enumeration and multi-ask expansion in the board adapter. Define the single-row wire type `SeatEntry` from the following field inventory, including legacy nullability. The entry carries an explicit observation for each attention group (turn/question, host/permission, bridge, classifier, dismissal, finished-work and routing). Use `observed(value | null)` or `unresolved` on the wire. Observed null requires a current source and a successful lookup. An unavailable, busy, stale or incomplete optional source yields unresolved immediately. Read each ready projection and its source watermark together, with a final version check for cross-store reads. Use a nonblocking probe for optional reads and abandon enrichment on contention. The identity deadline is never a wait budget for enrichment. When any prerequisite of the winning reason, dismissal or route is unresolved, keep that decision unresolved too. Never infer idle, operator ownership or a safe action from missing evidence. The pane opens with its authorized title and messages. Show “Checking attention” in its status area, suppress unresolved actions, and reconcile the badge in place without remounting or losing a draft. Pass observation readiness alongside the entry to the shared seat-state derivation in `seatState.ts` and to the pane’s attention controls. Only evaluate the final `attentionId` or enable reason-specific actions when its inputs are observed. The board adapter already has the full inputs and keeps its existing representation. Use the current authoritative rename if present, otherwise the pinned file’s readable display title. Linked review/task decoration may refine a fallback title after opening. Use a mapped type checked against the keys of `FileEntry` for the owner inventory. A new field must acquire an owner or an explicit inapplicable case before it can reach a seat. A plain scanner row cannot satisfy the seat hook's result type.

## Deferred — not currently justified

**Engine split and behavioral selection.** The design considered moving 4,007 lines into launch, settlement and publication modules, keeping shared controller changes on full coverage. The review replayed every zero-context engine hunk on parent and child across the 42 first-parent commits from `git log --first-parent --since=2026-11-06T10:25Z --until=2026-11-20T10:25Z --format=%H 50e53c0031 -- src/lib/pipelines/engine.ts`. Two commits (`97d224fbfe`, `4fe10c6a11`) localized to launch and one (`2451da7daa`) to settlement. Four also changed imports or declarations absent at the base, and 35 touched the shared facade. The frozen inventory has 26 launch, 43 settlement, five publication and 16 transition files. Including required secondary owners gives selections of 90, 90 and 64 respectively. No commit localized to publication. **Zero of 42** would get a smaller set under this cut. Counts describe selection and make no CPU claim. A future proposal would need to demonstrate a smaller safe selection on actual changes around patching, admission, port wiring or run-stage ticks before moving those declarations.

**Local forgery resistance.** A writer with control of the shared checkout and cache can fabricate local evidence or replace its hook. A checksum detects corruption and does not authenticate that writer. Protecting against such a writer would also require trusted publication entry points outside the checkout. The requirement permits local reuse when the implementations share trust. Separate verification identities, a privileged installation, protected storage and forgery fixtures would serve a different requirement and are deferred.

General-purpose event sourcing, a new conversation database, redesigning the board cache or search, deletion based on directory names or age, changing Docker retention policy, remote sharing of arbitrary test receipts, a replacement broker, and a repository-wide rewrite of the pipeline engine fall outside this request. Each chosen change has a concrete consumer and a measurable deletion.
