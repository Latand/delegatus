## Observation 1: OpenAI has a Decisions API

Observed in official OpenAI documentation on 2026-10-29. The [Decisions guide](https://developers.openai.com/api/docs/guides/decisions) states:

> Send requests to `POST /v1/decisions` using `gpt-6-luna`, the only currently supported model.

The [create-decision reference](https://developers.openai.com/api/reference/resources/decisions/methods/create) documents `input`, `model`, and an array of `questions`. Its predicate question returns `probability`. It also states:

> Any question can return a refusal instead of an answer

The official request contract supports the following adapted example for Delegatus. Authentication is a server-side OpenAI API bearer key; the URL is `https://api.openai.com/v1/decisions`.

```json
{
  "model": "gpt-6-luna",
  "input": "The agent message being evaluated.",
  "questions": [
    {
      "name": "asks",
      "type": "predicate",
      "instructions": "The message asks the human operator a question or asks the operator to reply, choose, confirm or approve something."
    }
  ]
}
```

This example adapts the first existing Jev statement from `src/lib/asks/jev.ts:24`. A production request would include the existing `waiting` and `decision` statements as two more named predicates. Match returned answers by `name`, validate finite probabilities in [0, 1], and handle missing, duplicate and refused answers before applying a threshold. The reference permits 1–400 questions and returns an `answers` array with token usage. These are observed API capabilities; equivalence of classifier quality remains unmeasured.

### How this differs from today's Jev request

The existing implementation sends `model: "typesafe/jev-1.13"`, a structured `state`, and a question object keyed by name with `type: "noul"` to OpenRouter's `/api/alpha/decisions` (`src/lib/asks/jev.ts:14`, `src/lib/asks/jev.ts:114`). It expects `answers[name].noul` and a dollar-valued `usage.cost` (`src/lib/asks/jev.ts:134`). OpenAI documents neither that `state` field nor the `noul` question type. It documents `predicate`, `choice`, and `score` instead. An adapter must translate both the request and the answer.

For structured state, OpenAI accepts a user message containing `{"type":"input_json","data":...}` in `input`. The memory-offer path also puts objects in Jev question instructions (`src/lib/memory/selection.ts:98`); those must become text or supported content parts with the evidence preserved. OpenAI probabilities need a fresh labeled evaluation before reusing Jev's attention threshold of 0.85 or the role selector's 0.3 cutoff (`src/lib/asks/jev.ts:17`, `src/lib/memory/roleSelect.ts:161`).

Recommendation: offer OpenAI Decisions as an explicit alternative for all three classification features below, retaining OpenRouter as their initial provider. The nearest general-purpose alternative is [Responses with Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs). It can generate schema-conforming objects, but generated confidence fields would need their own calibration and token accounting. Decisions already supplies the typed probability needed here. Changing only the endpoint and key would break the current parsers.

### Supporting API calls and excluded paths

The role-memory call currently evaluates a **shadow** selection on pipeline starts: `src/lib/memory/roleLaunch.ts:85` records scores and selected IDs, while the delivered block remains the whole snapshot (`src/lib/memory/roleSelection.ts:63`, `src/lib/memory/roleSelection.ts:110`). The regression at `src/lib/memory/roleSelection.test.ts:143` asserts that distinction. Its provider switch must preserve shadow mode; it must not silently change which rules agents receive.

Voice catalog requests use the selected ElevenLabs, Soniox or Fish credential (`src/lib/ttsVoices.ts:60`). They list built-in/cloned voices and occasionally retrieve the selected voice: ElevenLabs `/v2/voices` and `/v1/voices/{id}`, Fish `/model`, Soniox `/v1/tts-models` and `/v1/voices` (`src/lib/ttsVoices.ts:87`, `src/lib/ttsVoices.ts:97`, `src/lib/ttsVoices.ts:105`, `src/lib/ttsVoices.ts:123`). They support TTS; they are not independent synthesis features or proven billable calls. OpenAI currently has `voiceList: false` (`src/lib/ttsBackend.ts:119`). Provider voice IDs, clones, encodings and alignment metadata cannot be carried across as though they were interchangeable. The current TTS cache is told the actual billed provider/model/voice by server headers (`src/app/api/tts/route.ts:133`).

Telegram needs an explicit absence in the inventory. The bot recognizes `voice` and `audio` message kinds, storing text or caption when present (`src/lib/telegram/bot/store.ts:141`, `src/lib/telegram/bot/store.ts:534`). The personal connector similarly reports media kinds (`vendor/telegram-mcp/telegram_mcp/tools/messages.py:40`) and can send an existing OGG/Opus voice file (`vendor/telegram-mcp/telegram_mcp/tools/media.py:202`). No transcription, paid speech generation or use of the five service keys was found in those modules or their connector entry points. External relay media input admits photo/document types (`src/lib/externalRelay/mediaInputValidation.ts:3`, `src/lib/externalRelay/mediaInputValidation.ts:25`); remote services may transcribe before delivery, but that cannot be attributed to Delegatus. Telegram transcription would be a new feature using file transcription after an explicit audio-download/conversion path. Do not show an operative Telegram provider switch in this prototype.

The ChatGPT dictation path calls `https://chatgpt.com/backend-api/transcribe` using signed-in Codex credentials (`src/lib/transcribe/chatgpt.ts:13`, `src/app/api/transcribe/route.ts:101`). It supplies no OpenAI API key. Keep its existing opt-in and authentication distinct from a new OpenAI API backend.

Call-memory summaries are another possible API use, but today they run the managed Claude subscription CLI with `claude-haiku-5-5` (`src/lib/voiceCompanion/callMemory.ts:11`, `src/lib/voiceCompanion/callMemory.ts:17`, `src/lib/memory/profileModel.ts:24`). Memory profiles similarly use CLI-backed structured output (`src/lib/memory/profileModel.ts:62`). OpenAI Responses with Structured Outputs could perform those tasks, with new accounting and quality evaluation; they do not presently spend the listed service keys. Preserve them as deferred candidates.

The broader endpoint search found no first-party embedding, image-generation or translation API feature to migrate. GitHub metadata/publication, Telegram transport, package/model downloads, subscription usage reads and arbitrary added MCP tools serve other purposes. Their credentials and remote behavior remain outside this service-key selector. API-key filtering in `src/lib/environmentIsolation.ts:4` and `bin/server-runtime.mjs:10` handles credential inheritance only.

### Proposed storage and reads for the later build

Use the existing key catalog as the only credential source. Store service choices separately from secrets. The simplest shared addition is a small versioned config document, for example `configFilePath("api-services.json")`, containing an opt-in OpenAI override per classification feature and per dictation/read-aloud feature. This file is a proposal; it does not exist in the audited revision. Leave native provider settings as the remembered baseline while the override is active. Saving a key alone leaves every override off and preserves current behavior. Existing OpenAI TTS or API voice selections remain represented as current selections.

One request-time resolver should return requested provider, effective provider and the short reason for a fallback. Attention, conversation-memory dispatch and role-memory dispatch must all consume it independently. TTS and dictation availability/configuration endpoints must report the same effective provider that their synthesis, token and upload routes dispatch. Existing feature menus must edit the same effective choice and baseline; otherwise a Keys toggle and a mic/read-aloud selector would disagree. An explicit feature-menu choice must update the retained baseline even when it equals the active override, so removing the key cannot undo that explicit choice. Provider-specific model/voice preferences remain in their current stores. Changes must use asynchronous admission on Viewer paths and a bounded read; no repeated whole-history scan is needed.

Voice can use its existing backend field and retain a prior backend when explicitly changed through the new surface. Keep one voice feature choice covering both API Live and API Responses. Keep feature enablement separate: selecting a provider must not start a call, enable attention, enable a memory scope, start a recording or submit a paid key test. Explicit environment provider overrides keep their existing authority and lock reason; do not show an effective provider different from the backend the server will actually use.

## Removing a key and continuing work

Today there is **no delete action** in the Keys route (`src/app/api/keys/[id]/route.ts:12` exports PUT only). The proposed key-removed prototype state therefore previews future behavior. With a selected key missing, today's TTS returns 503 (`src/app/api/tts/route.ts:157`), selected ElevenLabs/Soniox batch transcription returns 503 (`src/app/api/transcribe/route.ts:58`, `src/app/api/transcribe/route.ts:76`), and API voice throws `NO_KEY` (`src/lib/voiceCompanion/storage.ts:368`). A missing OpenRouter key skips attention (`src/lib/asks/sweep.ts:89`), skips optional conversation offers (`src/lib/memory/controller.ts:160`), and retains BM25 role selection (`src/lib/memory/roleSelect.ts:121`). Automatic restoration of the previous provider is new work.

For the later build, resolve an unavailable OpenAI override back to its retained native provider on the server before issuing a new request. Apply this for UI deletion, external file removal, unreadable/empty files, process restart and environment changes. Preferences may remember the explicit OpenAI choice while it is unavailable; show the **effective** previous provider and the missing-key reason. Re-saving a key restores an explicitly remembered choice, but never creates new opt-ins. This makes the re-add behavior explicit in the prototype.
