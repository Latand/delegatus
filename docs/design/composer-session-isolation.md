# Typing while other conversations are active

The 2026-11-24 request for issue #4285 asks that a person typing into a conversation on a busy board see keystrokes appear as promptly as in a plain field on that board. The editor must still respond to their conversation, loss or recovery of the connection, and the fate of their send. The implementation needs a visual critic to measure the changed field before and after. The requirement comes from the 2026-11-20 architecture review, §6, lines 61–69, and issue #4285.

## How a foreign event reaches the screen

1. An SSE message enters `handleEnvelope`. A heartbeat updates the last-event time. An accepted envelope installs the reduced store, a duplicate confirms health, and a revision gap requests a snapshot. The reducer knows the conversation it writes. In particular, a receipt has an operation ID **and** a conversation ID. An attention resolution can recover its owner from the stored attention. The bus batches general notifications on a 16 ms timer and calls every general listener. Files revisions also have a dedicated notification. ## Decision

**Route accepted changes to the readers that own them.** Keep the existing transport, reducer, draft owner and files cache. Add keyed notification to the tab's runtime bus and attach the board status overlay to the current catalog. Look up the identities changed by an accepted event. If conversation B has no row or aggregate on the screen and supplies none of conversation A’s controls, its update must cause zero row evaluations there and zero notifications to A’s editor.

## Visual critic protocol for implementation

1. **Freeze the comparison.** Extend the existing board geometry driver for the production page and use the existing conversation/phone drivers for state checks. Use a disposable Viewer and fictional data, isolated profile and state roots, fixed browser build, fonts, zoom, device scale factor 1 and 60 Hz display. Record both source revisions, driver and fixture digests, seed, browser version, active screen, DOM element count and session/card counts. Run one foreground page at a time. The project's driver policy and existing field-cap assertions are in `AGENTS.md:380-399` and `scripts/capture-board-geometry.ts:4677-4697`.
2. **Set a repeatable load.** Seed 1,710 structured hosted conversations across two projects, 1,500 in the displayed project including its open seat, 210 elsewhere. Begin idle with no retained turn ID. Populate real card contents and pipeline strips in the fixture. Calibrate the desktop full board on the base to 23,500 DOM elements ±10%, then freeze the data and layout across revisions. Record the phone's actual mounted count. Replay an identical sequence at **6 accepted SSE events/s** from an independent clock, sending one event every 1/6 s. Start a turn in the other project, send it two text deltas, start an in-project sibling turn, then end the foreign turn and the sibling turn. Cycle target pairs deterministically and advance scope revisions and sequence numbers. For the separate accounting pass, alternate six start/end pairs for one foreign conversation at the same rate while typing the 37-character prefix of the test text. Record offered, received and applied events and the actual rate. The fixture size and board scale come from the 2026-11-20 architecture review, §6, line 65. The browser measurement note cited there records 6.0 messages/s at line 47.
3. **Pair each field with its control.** Use the seat input on the full desktop board at 1440 × 900, the phone conversation reached from the loaded board at 390 × 844, and the product's normal layout at 915 × 872. Record the phone’s mounted board or retained navigation state so both revisions exercise the same screen. On each screen compare the real field with a plain native textarea over the *same* loaded screen, in the same position, dimensions, font, wrap mode and initial text, with the same stream and focus. Keep the composer mounted during the plain-field run. Repeat both quiet (0 events/s) and loaded (6/s) cases. Alternate base/candidate and composer/control order. Fix the seed and initial cursor for each run.
4. **Time every printable key.** Warm up with 20 keys, restore the draft and caret, then dispatch 120 trusted printable keystrokes at 100 ms intervals from the driver. Use the five-character sequence `type ` repeated 24 times and record actual dispatch times. Capture each keydown's browser `timeStamp`. Its matching trusted input establishes the edit sequence. In the first subsequent animation-frame callback observing that prefix in the focused field, sample `performance.now()`. Subtract the keydown timestamp on that document's clock. Assign a shared frame to all edits it contains and retain every sample, including stalls. Check final text, count and focus. This measures time to the next frame callback. 5. **Report and judge.** Run five paired repetitions per width/load on each revision. Record a dropped edit, unexpected blur or missed accepted update as a functional failure.
