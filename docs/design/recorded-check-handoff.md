# Recorded check handoff

## Decision and scope

Keep the exact native Codex host that owns a recorded command until that command closes or its original deadline requires cancellation. Register the run, its receipt and its required roots before acknowledging the handoff. A serving Viewer observes completion, stores a durable result, and sends one keyed notification to the project's seat. An explicit acknowledgement of the current result and evidence revision releases the run's retention holds.

This uses the native socket host's existing restart handover. It avoids transferring a running process, rewriting a service's owner, or launching a replacement command. The host hold covers one registered obligation. It ends independently of result acknowledgement; unread evidence can outlive the host.

The change covers local recorded Codex stage checks. It adds no seat timer, model wait turns, UI, publication retry policy, account policy, or general job scheduler. Existing recordings without verified handoff remain readable through their current foreground wait interface. They acquire no survival guarantee.

## Records and identity

Use one new recorded-check module and the existing state database. Its interface has handoff, bounded read and acknowledgement operations. No existing MCP method implements these operations today. Add one `recorded_check` MCP tool with those three actions and matching authenticated Viewer route handlers. Use the existing tool service, caller attribution, capability policy and receipt recovery. Do not overload `pipeline_checks`, which changes execution settings.

The tool accepts a local ticket for handoff; it never accepts a command to launch. Execution stays in the stage's existing background-command facility. All ownership fields below are derived or verified by the server. A caller cannot select another attempt, project, host, seat, service or evidence destination by submitting identifiers.

Separate immutable run input from mutable observation and consumption:

| Record | Required content |
| --- | --- |
| Run descriptor | Schema version; random run identity created with the exclusive sidecar; descriptor digest; command/argv and working-directory binding; script and frozen source digest; exact ordered selection and expected count; tool/configuration fingerprint; required completion-report paths; original start and deadlines. Private command text and paths stay in private storage. |
| Attempt binding | Canonical project, lane, stage, attempt number, launch, conversation, session generation and stage-definition digest, resolved from the caller's native attribution and current registry membership. Include the accepted stage/runtime/privacy fence; record the source receipt that proved it. |
| Execution custody | Native socket endpoint and process identity, signal-domain identity when present, recorder identity, gate-wrapper identity, and each subsequently admitted supervisor/guardian/service identity. Process identity includes boot and namespace epoch plus kernel start identity. A service additionally carries its unique unit, invocation and cgroup identity. |
| Root holds | Exact registered creation record, physical path and device/inode, launch owner and purpose for each required scratch/configuration root. Required files are relative entries within those roots; output directories may contain files created later. Record source exports, scripts, selection, configuration dependencies and patches as well as logs and results. |
| Observation | Monotonic row revision; observing Viewer identity/epoch; queued/running/cancelling/terminal or custody-unknown state; actual wrapper exit; actual command exit or signal if observed; cleanup evidence; observed selection counts and completeness; terminal receipt and evidence digests. Missing facts remain nullable with a reason. |
| Consumption | Stable result identity, result revision/digest, one notification key and operation binding, confirmed destination, explicit acknowledgement actor and evidence disposition, per-root release/retirement state and bounded reason. |

Keep the authoritative registration and result in a private `recorded-checks` state collection outside disposable scratch. Use a private evidence directory beneath the state evidence root for retained terminal files. The collection records paths and hashes; large output stays in files. Use the existing durable-write helper for files and the existing asynchronous state admission for database writes. All SQL must compile on SQLite 3.39.

The sidecar remains an execution producer's output. After handoff, its path is insufficient authority by itself: the stored descriptor digest, original directory identity and producer identities bind every import. A copied sidecar and existing hardlinks do not subscribe to future results.

Two epochs have different purposes. The execution owner remains the original native process and recorder. Viewer restart can advance the registry writer claim and the observer epoch while retaining that same execution owner. Every observation write and send checks the current serving release and observer revision. A stale Viewer cannot publish after its replacement takes custody. The original writer epoch is evidence of admission; requiring it to remain the current epoch would break legitimate restart handover.

## Launch and verified handoff

Extend `gate-wait.ts` with an explicitly handoff-capable recording form: `--record LOG --manifest MANIFEST -- COMMAND...`. This is a new form. Preserve the existing command form and bounded `--wait` behavior. The production manifest builder constructs the descriptor before execution from the actual source export, script, selection and check configuration. Tests use that builder. A revision name alone cannot bind dirty or ignored source inputs.

The manifest names a finite original absolute custody deadline and the existing execution allowance. The recorder owns the absolute timer, so it remains enforced while every Viewer is down. Anchor its remaining duration to a monotonic clock before spawn; persist the wall deadline and boot/clock evidence for recovery. Wall-clock changes and observer restart cannot renew it. Nested gate allowances, ancestor deadlines and cancellation remain authoritative. A handoff cannot lengthen any of them. Queue time continues to be excluded from the execution allowance; the separately declared absolute deadline bounds total custody, including a queued run. The caller chooses it when recording starts. Legacy recordings lacking this evidence cannot be upgraded by inventing a fresh deadline at checkpoint time.

The launch sequence is:

1. Exclusively create the log/sidecar. Persist the descriptor, recorder identity and absolute deadline before spawning the gate wrapper. Set a run binding in the wrapper environment, with the selected sidecar as a producer output location. Drain both output streams.
2. Capture the wrapper's identity before the first await. Persist a direct parent/child binding. Extend the existing owned-runner paths only to publish run-bound supervisor and dispatch/close evidence. Queued state has a live recorder and queue wrapper; there may be no service yet. Running state requires the admitted supervisor's evidence. The old `running` marker alone is insufficient.
3. Once the background tool reports recording started, call `recorded_check` with action `handoff`, the ticket and manifest reference, using one stable request key. Do this once. The server resolves the calling stage and validates the descriptor, roots, deadline and actual custody.
4. Under the same asynchronous sweep-admission lease used for attempt-root retirement, validate root creation records and reject roots already quarantined or under an unreconciled deletion intent. Recheck the caller/attempt and host after I/O. Commit the run registration and root holds atomically in state. Install completion observation before its initial snapshot read. Then re-read the descriptor and owner/terminal evidence and commit acceptance under the current stage fence.
5. Return either `custody-accepted` with the immutable receipt identity and deadline, or an explicit refusal/interrupted/unknown result with the missing observation. A timeout leaves the response uncertain; retry the same request key to read the original admission. No retry launches a command.

Prove custody by matching the verified native socket owner to the registry, the recorder/wrapper to that host's captured descendants or signal domain, and a service to the wrapper's actual invocation. Verify liveness and start identity in the correct PID namespace. Check permissions and directory identities without following a caller's symlink. Permission failure, conflicting membership, an unverifiable process, a stale stage, missing source proof or an absent required root prevents acceptance. Record whatever partial evidence can be established; never turn a host exit into a command exit.

Registration has explicit `preparing`, `accepted` and `refused` admission states. Preparing holds the registered roots and blocks automatic retirement while the bounded verification finishes. A crash in that interval leaves a recoverable reservation. On restart, prove the same live custody or terminal report before accepting it; otherwise settle admission as interrupted/unknown and retain the evidence. The original deadline also bounds this reservation. A replay cannot transform missing proof into acceptance.

The final admission transaction must read the relevant stage/control/registry revisions while holding its write authority, so stage close or a new launch cannot slip between validation and registration. Serialize handoff with automatic termination through the existing registry operation lock for that exact host. Handoff waits at most thirty seconds for that admission; refusal leaves the existing owner untouched and grants no custody. The stop path keeps its reservation through the signal ladder; handoff cannot accept custody between the last eligibility check and its signal. A pending stop whose dispatch is uncertain also prevents acceptance. Lock order is host operation lock, attempt-sweep lease, then short state transaction. Sweep never acquires a host lock. Do no I/O while holding the state write transaction. Revalidate immediately before each destructive signal, including after its asynchronous checks. If a stop won first, handoff reports the loss; if handoff won first, automatic idle retirement defers. Every prepared retirement/startup projection must include the recorded-check collection revision in its validity fence, even when its pipeline row did not change.

After acceptance the stage can report `needs_decision` and end its turn. `stage_report` reads the run index for that exact attempt. It permits this checkpoint and returns the durable custody receipt. A pass/fail that would advance work while required checks remain active is refused with the outstanding run identity. Claude's existing transcript obligation semantics remain separate. A needs-decision report with an unverified ticket explicitly records interrupted/unknown custody and preserves partial evidence; it promises no survival.

## Host hold, deadline and restart

Expose a narrow predicate for an exact host or launch: this run still requires its original execution owner, through its original deadline and bounded cleanup. Apply it at:

- controller terminal-host candidate selection and `pipelineHostHasLiveWork`;
- the compact retirement projection and the runtime's last automatic-kill authorization;
- startup's settled-stage filtering and verified socket reconnection;
- demotion/reconfiguration paths that might release that owner;
- dead-producer recovery decisions and worktree/scratch cleanup that could remove live inputs.

The predicate does not change the attempt's model-turn activity or manufacture a busy turn. It is keyed durable work. A settled attempt can need observation of an existing host without needing a new model turn. A startup path for such an attempt reconnects only to the recorded socket/process; it must never fall through to orphan termination followed by fresh engine creation. Loss of reconnect proof is a custody-unknown observation, with roots retained. Ordinary launches on all supported platforms remain available. A host without restart-capable native custody receives an explicit unsupported/unknown handoff result; that capability limit does not prohibit launching the stage.

A replacement Viewer loads active rows in bounded pages, installs watchers, reads their current receipts and reclaims observation under its serving epoch. It can discover a result written while no Viewer existed. A runtime-host restart similarly recovers existing notification operations through its normal journal. Neither restart recreates the command or resets its deadline. Reconnect the existing native owner without sending a continuation. Protect recorded obligations from generic restart notices that would request a rerun or wake an agent merely to wait.

At the original absolute deadline, the recorder requests cancellation through the exact existing wrapper/supervisor path. A cancellation from close, explicit stop, retry or runtime replacement is durably recorded before signalling. Use the existing identity-fenced cleanup ladder and its bounded attempts. If an action necessarily terminates the host, cancel/reconcile its run first; changing an attempt number alone cannot release custody or evidence. A fresh stage cannot bind an old run as its own verification.

Natural close can race cancellation. Store command close, cancellation request, wrapper close and cleanup observations separately. An actual command exit remains available even when the overall check failed cleanup or was cancelled. A queue cancelled before dispatch has no command exit and no executed selection. Deadline expiry supplies an expired reason; a command exit requires its own close evidence. The legacy wait process's exit 124 can mean an active wait timeout; it never supplies terminal evidence.

Once terminal producer and cleanup proof is durable, remove the run's host hold. An evidence copy still pending keeps its root hold and does not require an idle engine to stay alive. Result acknowledgement is not needed for host retirement. If cleanup cannot be confirmed, retain the existing unconfirmed-termination custody and evidence, with the exact missing observation. The new hold itself never extends past the original deadline and bounded cancellation attempt. Identity uncertainty never authorizes a kill. Other live work sharing a host continues to protect that host through existing rules.

## Completion owner and result delivery

Use one bounded event-driven observer in the serving Viewer. It watches registered sidecar directories, subscribes before the initial read, and rechecks on completion rename, native owner exit, cancellation, startup and the original deadline. A watcher failure records an observer fault and performs one bounded reconciliation; it cannot silently discharge the run. The original deadline read also recovers a missed filesystem notification. Do not tail output repeatedly or schedule seat wakes to look for progress.

No database lease, pipeline mutation or controller job slot is held for the duration of a command. Native owned-runner liveness/watchdog checks keep their existing responsibility. Observer work carries a loop-monitor label and performs keyed, indexed reads. Hashing/copying large evidence streams runs outside the serving loop's synchronous sections under a bounded operation; failures leave retention in place.

On close, the producer writes a structured run-bound report in addition to the legacy integer exit file. Extend each real supervisor path to retain the actual command code/signal and cleanup outcome before its own close. The recorder's wrapper exit stays a separate field: a service failure, spawn error or survivor refusal may differ from the command's result. Flush report files before publishing their completion rename. On spawn failure, record infrastructure failure with a null command exit.

The observer then:

1. Validates the original descriptor, producer, directory identity and close evidence. Reads the required completion manifest and final per-file results. Missing final ran-count or incomplete per-file evidence keeps verification incomplete even if an outer script returned zero. For a multi-file campaign retain expected, visited and completed counts independently; a traversed timeout is still incomplete verification. A single command can use a one-entry selection.
2. Retains the terminal receipt, final manifest, logs, source/script bindings and declared patches in private evidence storage, with hashes. A failure to retain bytes leaves a recorded terminal observation and an evidence-pending hold; it cannot release roots. Preserve real failing outcomes.
3. In one state transaction stores the terminal result and its notification obligation. The result identity is the run identity. Duplicate close events and overlapping observers converge on that record. Result bytes and selection remain attached to their original source digest after the worktree changes.
4. Resolves the project's current seat and reserves one notification key derived from the run identity. Save the destination, seat epoch, payload digest and operation binding before actuation. Use the existing structured delivery and original-send settlement path. The bounded message names the outcome, count completeness and durable receipt reference; it contains no raw private logs, configuration values or public report publication.
5. Confirms delivery against the original native operation and destination evidence. Queued, sent or uncertain stays distinct from delivered. After a lost response reconcile the same operation. A terminal uncertain send receives no new key. A seat rotation before admission can choose the successor; after reservation use the existing channel withdrawal/redirect protocol, with the same logical result key. A possibly delivered message to the old seat prevents a second completion. With no seat, keep a pending lane result and wake delivery on the existing seat-designation event.

Add the result-key namespace as a channel completion in seat routing. Keep it distinct from periodic tick/epoch messages. Generic spawn notices must not create a second notification for this pipeline-contained obligation. Successful completion wakes the owning seat for useful work once. The original stage remains parked until normal owner-directed continuation; no automatic `retry-stage`, graph transition or command replay follows the notification.

An explicit refusal before dispatch permits the reservation to move to the current seat under the same completion key. Persist that refusal and clear its authority before attempting the successor delivery. A registry lookup with no matching operation alone grants no such authority; an existing or uncertain operation keeps its original binding.

Owner loss with no reliable close produces one durable interrupted/unknown result and an unresolved custody record. A later matching report refines that same result through a new revision with reconciliation history. It cannot overwrite the unknown interval or change the run/source identity. It creates no second completion notification. Consumers read the current revision from the stable receipt; an acknowledgement for an older revision fails.

## Retention and acknowledgement

Hold roots by registered creation record and physical identity. Select only the minimum existing cleanup units containing the run's required files. A scratch root containing the frozen export, script and patch may be one such unit; the paired configuration root is held only when the run depends on it. Account homes, shared caches, other attempts and arbitrary same-prefix directories are never adopted as run roots. A worktree needed as live input receives an exact dependency hold, without granting permission to delete it later.

Pending, cancelling, evidence-pending, cleanup-unknown and unread terminal results keep their registered roots. Settlement, lane close, root release callbacks, age/cap pressure and a missing original path do not override those holds. Keeping the original directory covers late-created files and renamed exits. Treat the ledger as authority even when an attempt root is absent: record missing evidence and retain its surviving dependencies instead of forgetting the obligation.

`recorded_check` acknowledgement requires the current result revision/digest, the evidence manifest digest and a retention disposition. The server authenticates either the owning stage's permitted consumer, its project's current owning seat, or the operator; it records who acknowledged. A former seat's receipt replay can return its original acknowledgement, but it grants no new authority after rotation. Merely reading the result, delivering the notification, accepting a stage report or finishing a lane acknowledges nothing.

For release, require terminal producer/cleanup proof and verified retention of every required file in durable storage. The acknowledgement confirms that manifest and identifies which original owned roots can be released. Its disposition either adopts the retained files as the consumer's canonical evidence output, or confirms a verified consumer-owned copy. The server selects and validates the private destination from that consumer's project/attempt authority. Record the new evidence owner before releasing the old roots; never assume that an unrelated cleanup subsystem will retain the files. Promote terminal files in place where possible and remove only verified duplicate staging copies. Configuration roots may be released after acknowledgement and the run's last owned user exits; do not archive credential bytes into the result. Retain only the configuration fingerprint needed to interpret evidence. External references, mounts, Git dependencies, changed root identities and existing preservation markers can still block deletion.

A terminal cancellation can leave declared outputs absent and verification incomplete. After confirmed cleanup, record those absences through owned, direct directory components and retain every existing byte before allowing acknowledgement of the partial result. Recheck each absence at release. An unreadable file, an indirect path or unverified custody keeps the hold; acknowledgement never changes the verification outcome.

Synchronize handoff/root-hold changes and sweep deletion using the existing asynchronous attempt-sweep lease. The root hold check must run before measurement/eligibility, again after every awaited inspection or copy, after quarantine and immediately before removal, including deletion-journal replay. A final revision check without that shared exclusion leaves a registration/deletion race. Never hold the sweep lease while awaiting command completion or model activity. A handoff arriving after quarantine must fail or reconcile that exact intent before acceptance; it cannot create a hold on a recycled pathname.

Before forgetting an attempt root, persist its retirement intent in the recorded-run row: original physical identity, acknowledgement/result revision, reason, time and cleanup-journal reference. After removal record the outcome, then allow the old root row to be forgotten. Interrupted cleanup replays the same intent. A missing path without matching intent is `missing-unexplained`, with no invented removal actor or time. Bound reason text to 1 KiB and keep it beside the compact receipt.

Bound the new machinery with implementation constants: at most four unacknowledged registrations per attempt and 128 per installation, at most 32 rows per recovery/delivery pass, a 64 KiB registration/result metadata envelope and a 16 KiB read page with `truncated:true` and continuation. These are proposed internal bounds and require no new operator settings. Capacity refusal never evicts an unread result or cancels its command. A handoff refusal leaves the stage responsible for preserving evidence and yielding an interrupted/unknown checkpoint. Pagination resumes beyond completed or suppressed rows.

Move acknowledged result metadata, the consumer's evidence-custody receipt and the small replay/retirement tombstone into the owning pipeline's durable history before dropping the hot observation row. The tombstone retains the run identity, descriptor/result digests, acknowledgement and notification binding, so late events cannot recreate a delivery. Keep it for the lifetime of that archived pipeline's receipts. Retained files are the consumer's declared evidence output; keep one canonical copy and no additional recorded-run archive. An acknowledgement without proved evidence custody leaves the run open. Unread rows occupy the bounded backlog until consumed. Disk pressure reports those holds and may refuse new custody; it cannot expire unread evidence.

An acknowledged result whose completion delivery is pending keeps a compact active row within the same backlog bounds. It holds no original root or native host, and its observer reads the frozen result from the ledger. Delivery settlement updates durable history and retires that active row; acknowledgement alone cannot discard the completion obligation.

## State and race contract

| Transition or race | Required result |
| --- | --- |
| Recorder has started; handoff response is lost | Replaying the original request returns the original run admission or the exact missing proof. Command count stays one. |
| Command finishes before or during registration | Subscribe-before-read imports its run-bound report and accepts a terminal receipt, or reports unknown if proof is incomplete. No stale running state can overwrite terminal evidence. |
| Queue becomes running while registered | The same run gains supervisor/dispatch evidence. Admission uses its original ticket, owner and budgets. |
| Stage report races idle termination | The common admission/signal fence orders them. Accepted custody prevents automatic retirement; a prior stop prevents a survival acknowledgement. |
| Controller restarts before/after result persistence or notification reservation | Recover from durable rows and original native receipt. Reattach observation and resume only missing projection/delivery work. |
| Native host stays alive but recorder dies | Record interrupted/unknown. A live host alone proves no campaign result. Reconcile any surviving service without replay. |
| Recorder disappears while a service still runs | Preserve service invocation/cgroup custody and roots; use bounded owned cleanup or await its original deadline. No fabricated command exit. |
| Caller substitutes another process, namespace, ticket, stage or root | Refuse the handoff/acknowledgement before any new custody or deletion. Retain a bounded diagnostic without echoing private values. |
| Deadline/close races a successful command | Preserve the actual exit and cancellation chronology. Check success additionally requires complete selection evidence and settled cleanup. |
| Result or source changes while copied | Abort that copy/acceptance; preserve the prior valid result and root holds. Retry observation under the same run identity within the operation budget. |
| Late result follows unknown or cancellation | Append matching evidence to the same result revision chain. Never revive execution, erase cancellation or send a second completion. |
| Acknowledgement races result refinement or new evidence | The result/evidence CAS refuses the stale acknowledgement. No root release occurs. |
| Sweep pauses after eligibility, quarantine or copy | Fresh root-hold/revision checks under the shared lease stop deletion when custody changed. Replayed deletion intents obey the same check. |
| Attempt retry, runtime switch, close or archive races completion | Preserve the original binding and result. Cancel/reconcile live custody where necessary. A successor cannot consume it as evidence for different source. |
| Notification lands before its acknowledgement is saved | Reconcile the original operation and destination; persist delivery once. Evidence retention remains until explicit consumption. |

## Deferred — not currently justified

- Migrating a live recorder into a different service or inventing a separate job daemon. The native socket owner already provides restart custody; process transfer would add a second ownership protocol.
- Replaying or cleaning earlier interrupted recordings. Their owning seat must reconcile the original supervisors after deployment, reuse complete per-file evidence for its exact source, and continue only confirmed unfinished work.
- Cloud/external job discovery, arbitrary detached commands and a general scheduler. This contract starts with a verified local recorded Codex run.
- Automatic stage retry, graph advancement, new seat clocks, repeated model waits, public result posting, or UI surfaces. Completion supplies one actionable durable result through the native delivery path.
- Broad retention disablement, account-home retention, cache duplication and unrelated cleanup policy changes. Existing preservation rules continue to govern every root after its run hold is released.
