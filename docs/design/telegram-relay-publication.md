# Telegram relay publication

The Celestia owner-private-chat and publish design, section 6, is pinned by
SHA-256 `a40867d40cc41866ac6419f70217add173abb3c1a9f2ece378007ee877924c85`.

Delegatus already claims `requester_context`. An owner request with all admin
flags false reaches the existing owner tier. Handoff items remain outside the
callable tool index. The private-loop test feeds stored review text and a
copied answer through the real Telegram sender and relay runner, recording the
same decision as the web review.

`externalRelay/publish.ts` sends confirmed Telegram text using the pairing
credential and relay version 1. It preserves the body through four bounded
attempts, waits the supplied 429 delay, and shares a queue per pairing. A 404
holds that target for five minutes; a 403 holds that target/chat for five
minutes. Unicode and encoded JSON limits are enforced together with a visible
truncation marker. Telegram send completion does not await publication.

The sender exposes its confirmed-message publication hook for ordinary text,
rich reviews and media captions. The review renderer supplies plain text with
variant descriptions, frame captions, questions, recommendations and copied
answer lines. Successful parts of a partial text send, operator test posts and
sign-in replies also publish their confirmed text with the bot identity retained
from before the Telegram operation. Uncertain sends have no confirmed receipt
to publish. Edits and deletions are
outside this protocol.

## Target binding awaiting a decision

At Celestia main `0997461ccf4d6e8752d03d3df2ed40ebc8187659`,
`apps/backend/application/usecase/clones/relay_protocol.py::_target_id` computes
an HMAC of the clone id using a service secret. `_target` returns that opaque
id, the name and routing settings. The name comes from the bot's first name
(falling back to its username) in
`apps/backend/infrastructure/database/repo/relay.py::list_targets`. It does
not identify a Telegram bot reliably.

The publish route requires this target id; Telegram confirms a send with a
bot identity and chat/message ids. No current field joins these identities.
Publishing to every target could store a review under the wrong clone,
especially in an owner's private chat shared by several bots in the service's
message table.

The production hook is therefore still unwired. Its publisher requires a
resolver that proves the connected Telegram bot's target, and returns no
match on ambiguity. Two possible completions:

- Celestia adds a bot-id field to its authenticated targets response. This
  supports automatic binding and is the recommended approach.
- Delegatus adds an explicit operator setting that binds a Telegram bot id
  to one paired target. This adds an installation configuration step.

The loop fixture supplies an exact synthetic binding in the test; it does
not establish a production binding or prove Celestia deployed either switch.

## Immutable install capture

`src/lib/externalRelay/fixtures/relay_v1/install_owner_private_loop.json` is
generated by `src/lib/externalRelay/ownerPrivateLoop.test.ts`, using the
production claim builder, sender, publish transport and decision runner.
The copied answer is decoded from the button in the actual Telegram request;
the private chat key is checked after schema parsing so it cannot silently
disappear from this regression.
An ordinary test run compares the complete bytes to the checked-in capture.
Regenerate only through that test by setting `LLV_RELAY_PRIVATE_LOOP_OUTPUT`
to the fixture path and running
`bash scripts/gate-slot.sh bun test src/lib/externalRelay/ownerPrivateLoop.test.ts`.
Use an isolated HOME, XDG configuration, state and temporary root, and a
closed loopback Viewer control URL, as required for all relay tests.
