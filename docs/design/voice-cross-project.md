# Voice Delegatus across projects

## Selected design

Build the small extension this request requires. Reuse the existing project identity, folder registration, orchestrator seat command, voice admission and message receipts. Add project discovery and a confirmed bootstrap operation. Keep ordinary work routed to the target project's orchestrator. A project name and optional objective should be enough once the installation has a default creation folder; after one spoken confirmation the server starts the orchestrator with its mandate as its first message.

Feasibility: high for discovery, reads and messaging; moderate for folder creation and bootstrap because their effects need durable recovery and authenticated human attribution. Named cross-project reads and delegation already exist. A generic agent launcher, a new orchestration service and a project-template engine would add scope beyond the requirement.

The operator selected bootstrap plus relay, one default parent folder, an objective appended to the standard mandate, and creation access for any active team member. The saved review has no comment and no outstanding question. These decisions govern every slice below. No ADR is warranted: these choices are reversible within the existing architecture.

Human authority, operation keys and account selection come from the server, never model arguments. Defaults remain the project frozen for the turn. An explicit foreign target never silently changes the browser view or the call's initial project.

## Project folder and preset flow

Existing project: resolve the exact canonical project; choose its recorded root first for voice bootstrap so an incidental recent worktree does not become the new seat's home. Validate cwd identity against the chosen project. If the recorded root is unavailable, offer another verified checkout from the same project; refuse rather than falling back to the Viewer's cwd or an unrelated folder. An existing seat returns its safe state and permits the separate task/message request.

New project: an unknown name remains an error for ordinary reads/sends. A creation request may explicitly enter the new-project branch. Choose the installation's default parent once from the known suggestion roots and persist that explicit human choice alongside voice settings after confirmation. Any active call owner admitted for creation may make the choice; bind it to the creation readback. If no root is selected, `create_orchestrator` returns `needs_root` with bounded safe labels and opaque root-choice references. Ask for one and carry its selected folder reference in the next `new_folder` argument. If the stored root becomes unavailable or no longer allowed, require a new choice. With an approved default root, propose a safe single folder name under it; reject separators, traversal and symlink escapes through the existing bounded-target code. The confirmation names the human-readable folder and objective. Root references resolve server-side; home paths do not enter provider prompts or speech. An already-existing directory is an explicit registration choice, never an overwrite or an automatic collision suffix.

Reuse `createManualProject` and project succession. Do not initialize git, clone, scaffold, write `AGENTS.md`, install dependencies or create remote repositories. A plain registered directory already works as a project. If git/origin is later added, existing identity succession must move the seat and task ownership through canonical aliases.

“Preset” initially means existing orchestrator engine/model/effort defaults, approved default mandate and normal server-side account routing. New projects use that same launch profile; project account restrictions still govern launch. Do not expose global `role_presets` or account-binding writes to voice. A named application/framework preset with file generation would need a separate requirement.

Treat a supplied mandate as the operator's project objective appended to the approved core, as selected. Leave `promptVersion` unset for the resulting bespoke mandate; preserve the objective's wording. This requires explicit composition in the voice seam: today's custom seat mandate is a full replacement. Preflight the composed envelope, including the role table, before folder or seat effects. Current tests reserve launch overhead and rotation-history room (`src/lib/orchestrator/prompt.test.ts:766`, `src/lib/orchestrator/handoffDigest.test.ts:439`); the history margin is particularly tight. Measure available bytes rather than assuming a 2,000-character objective fits. Refuse oversized text with an edit request, never truncate the mandate silently or rewrite the approved core to make room. Subsequent rotations use their existing history compaction and explicit oversized-core refusal.

## Authority and confirmation

| Caller | Reads and existing-seat requests | Folder/seat bootstrap |
| --- | --- | --- |
| Solo operator who started the browser call | Existing installation authority; resolve named projects and seat targets. | Allowed after the bound creation confirmation. |
| Active team owner who started the call | Same installation scope; preserve member authorship. | Allowed after the bound creation confirmation. |
| Active ordinary team member who started the call | Same permitted project reads and requests; there is no per-project membership ACL to assume. Preserve member authorship. | Allowed after the bound creation confirmation, matching human browser creation. |
| Revoked member, another call owner, anonymous client | Refuse before reading/caching or dispatch. | Refuse, including after a previously valid confirmation. |
| Backing API model, Codex thread, worker or service alone | Tools execute only within a live human-owned call. Model output is input to admission, never human identity. | No independent bootstrap authority; a forged `startedBy`, `operator`, member id or capability in arguments refuses. |

Current solo/operator and member identity are distinct. `requireOperatorAuthority` alone does not prove an active human team session, and an agent running under the same OS user gains no voice-bootstrap authority. Derive the caller at browser start; retain only the internal member reference; recheck call ownership, live session and active membership immediately before each effect. Owner-to-member role changes preserve creation access while membership remains active. Reusing a stored member id does not prove a session is still active: bind the new effect admission to the starter's live member session and revalidate expiry/sign-out as well as membership. Legacy calls lacking sufficient starter evidence cannot bootstrap.

Add a small shared human-admission seam around the existing seat command for browser creation and voice creation. Its voice branch consumes an admitted bootstrap proposal belonging to the verified call; callers cannot mint that proof. Preserve the browser route's existing policy, and admit every active team member in the voice branch. Do not manufacture a same-origin HTTP request with omitted agent headers and call that human authorization. Do not export a privileged generic command or run MCP with the operator's broad credential in the backing thread. Folder registration needs the same check before its in-process seam; it cannot inherit proxy checks it never traversed. Keep state ownership with the Viewer process.

Creation confirmation binds action kind, project identity or new root/folder reference, composed mandate digest, any initial task, resolved launch profile and starter. A later yes belongs only to the proposal visible for that answering turn. Changes to target, folder, objective, initial task or launch profile require a new readback; expiry, cancellation, hang-up or revocation invalidate it. Ordinary seat rotation may retarget an unsent message within the same project as today; it cannot retarget a bootstrap into replacement. Conditions, quotations and uncertain intent ask for clarification. Do not introduce a requirement that a provider supply complete audio transcripts: preserve the existing model-judgment contract while enforcing immutable proposals and later confirmation turns server-side.

Hard-to-undo work requested through a message gets the existing exceptional confirmation before delivery when appropriate. A confirmed send authorizes delivery of that request; it grants no new deploy, publication, deletion, account or service permissions to the receiving orchestrator. Voice exposes no rotation, deletion, role-mapping mutation or arbitrary worker-send tool in this scope.

Never expose account inventories/identities, provider usage windows or limits, routing bindings, secrets, bearer keys, auth files, member/session credentials, home paths or raw launch errors to either backing model or speech. Apply field allowlists and known-secret redaction before truncation, caching and provider serialization; transcript text is untrusted data. Speak bounded actionable errors such as “launch unavailable; open setup”. Existing approved voice spend UI remains a separate surface. Internal handles and receipt keys may support tools but never enter spoken sentences or public evidence.

## Execution and recovery

Extend the existing call storage with a small discriminated operation record: delegation versus bootstrap. Bootstrap can have a project/folder target before a recipient exists; forcing it into today's recipient-required proposal would preserve the very refusal being solved. Reuse confirmation events/cards and one resolver capable of both kinds. Store the immutable effect digest and derived registration/seat/message keys before dispatch. Deduplicate by the call, originating operator turn and normalized operation target/content, across provider call ids and reconnects. An explicit later repeat is a new operation.

Execution order: validate authority and full plan → await creation confirmation → revalidate authority/plan → register folder/project → execute seat intent with the recorded key → observe mandate/launch settlement → deliver an optional task request when the seat can accept it. Revalidate human authority after awaits and at the last admission point before every effect. Serialize conflicting registrations through the shared curation writer; the existing creation route lacks an idempotency key, so add a bounded registration adapter with an operation-to-identity record and exact-root verification. A duplicate belonging to another operation returns conflict; it must not become implicit adoption.

The filesystem and seat store cannot be one atomic transaction. Persist step outcomes so a retry resumes the unfinished step with its original key. Use existing seat intents and message receipts for their own effects. If a folder registered but launch failed, keep the folder and say exactly what remains. Never delete an operator directory as compensation. If a launch or send answer is lost, recover its recorded intent/receipt; never issue a fresh key or resend to a successor while the original outcome is unknown. After a call closes, recover receipts read-only and start no new step; subsequent work requires a live authorized call. “Starting”, “mandate delivered”, “task request queued” and “task created” remain separate outcomes.
