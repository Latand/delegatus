# Voice Delegatus across projects

## Selected design

Build the small extension this request requires. Reuse the existing project identity, folder registration, orchestrator seat command, voice admission and message receipts. Add project discovery and a confirmed bootstrap operation. Keep ordinary work routed to the target project's orchestrator. An existing project needs its name and optional objective. An explicitly new project also needs the spoken intent to create a new project; once the installation has a default creation folder, the server proposes its child folder. After the creation readback and one spoken confirmation, the server starts the orchestrator with its mandate as its first message.

Feasibility: high for discovery, reads and messaging; moderate for folder creation and bootstrap because their effects need durable recovery and authenticated human attribution. Named cross-project reads and delegation already exist. A generic agent launcher, a new orchestration service and a project-template engine would add scope beyond the requirement.

The operator selected bootstrap plus relay, one default parent folder, an objective appended to the standard mandate, and creation access for any active team member. The saved review has no comment and no outstanding question. These decisions govern every slice below. The server additionally requires a first-use target readback for each foreign project in a call; creation confirmation can satisfy it. This extends the new foreign-target surface while preserving immediate ordinary sends to the call’s original project. No ADR is warranted: these choices are reversible within the existing architecture.

Human authority, operation keys and account selection come from the server, never model arguments. Defaults remain the project frozen for the turn. An explicit foreign target never silently changes the browser view or the call's initial project.

## Project folder and preset flow

Existing project: resolve the exact canonical project; choose its recorded root first for voice bootstrap so an incidental recent worktree does not become the new seat's home. Validate cwd identity against the chosen project. If the recorded root is unavailable, offer another verified checkout from the same project; refuse rather than falling back to the Viewer's cwd or an unrelated folder. An existing seat returns its safe state and permits the separate task/message request.

New project: an unknown name remains an error for ordinary reads/sends. The required `target_kind` makes the branch explicit. “Create an orchestrator for <name>” uses `existing_project`; an unresolved name returns unknown/near matches and cannot propose mkdir. `new_project` is used only when the operator explicitly asks for a new project. Before proposing its folder, the server compares the name against the known canonical names using Unicode normalization, case folding and collapsed whitespace/punctuation, then bounded edit distance (at most one edit for short names, two for longer names). Suggest near matches for clarification; never auto-select one. A near-miss such as “Forge Demi” beside “Forgedemy” returns the existing candidate or asks whether a distinct new project was intended. Even with `new_project`, a near match prevents a folder proposal until the operator explicitly distinguishes it in a later turn. Clearing that ambiguity is bound to this target and proposal, and changes invalidate it. Choose the installation's default parent once from the known suggestion roots and persist that explicit human choice alongside voice settings after confirmation. Any active call owner admitted for creation may make the choice; bind it to the creation readback. If no root is selected, `create_orchestrator` returns `needs_root` with bounded safe labels and opaque root-choice references. Ask for one and carry its selected folder reference in the next `new_folder` argument. If the stored root becomes unavailable or no longer allowed, require a new choice. With an approved default root, propose a safe single folder name under it; reject separators, traversal and symlink escapes through the existing bounded-target code. The new-project confirmation says “new project, new folder <label>” and names the objective; an existing-project confirmation says “existing project <name>”. An unknown name alone can never advance to registration. Root references resolve server-side; home paths do not enter provider prompts or speech. An already-existing directory is an explicit registration choice, never an overwrite or an automatic collision suffix.

Reuse `createManualProject` and project succession. Do not initialize git, clone, scaffold, write `AGENTS.md`, install dependencies or create remote repositories. A plain registered directory already works as a project. If git/origin is later added, existing identity succession must move the seat and task ownership through canonical aliases.

“Preset” initially means existing orchestrator engine/model/effort defaults, approved default mandate and normal server-side account routing. New projects use that same launch profile; project account restrictions still govern launch. Do not expose global `role_presets` or account-binding writes to voice. A named application/framework preset with file generation would need a separate requirement.

Treat a supplied mandate as the operator’s project objective appended to the approved core, as selected. Leave `promptVersion` unset for the resulting bespoke mandate; preserve its wording. Today’s custom seat mandate replaces the core, so composition belongs in the voice seam. Append `\n\n## Project objective\n` (23 UTF-8 bytes) plus the objective; reject structural rotation/role-table heading lines in the objective with an edit request so future mandate splitting cannot discard it. Preflight the exact delivered text with the live role table before folder or seat effects, and verify that delivery preserves the objective byte-for-byte; if a legacy-section transform would change it, ask for an edit before admission.

Measured from current main under isolated state, using `mandatePreflight` (`src/lib/orchestrator/handoffDigest.ts:322`): the delivered default is **29,409 bytes**, launch overhead **742 bytes**, and the structured envelope **32,000 bytes** (`src/lib/runtime/structuredContent.ts:40`). Spawn headroom is **1,849 bytes**, hence at most **1,826 bytes of objective** after the 23-byte separator even before reserving rotation space. That is about 900 Cyrillic characters. The current 2,000-character instruction gate (`src/lib/voiceCompanion/liveGate.ts:17`) supplies no byte guarantee for an objective. The existing rotation-test formula gives **20 bytes**: `1,849 + 2,400 − 133 − 4,096`, using the retired task-list allowance, board pointer and history budget (`src/lib/orchestrator/handoffDigest.test.ts:439`). This formula is a test allowance, not actual free space beside a rendered handoff.

Use a server-computed UTF-8 objective ceiling: `min(1,000, spawnRoom − 23, mandatoryRotationRoom − 23)`, clamped at zero. Compute `mandatoryRotationRoom` by passing the unmodified approved core through `composeSuccessorMandate` with no history or optional notes and the largest mandatory handoff for the target project across the readable-current, readable-ancestor and no-readable-predecessor branches (`src/lib/orchestrator/seatCommand.ts:1560`). Reserve the supported maximum conversation-id width, use the live role table/scaffold, and revalidate these inputs on confirmation; changed inputs require a new readback. The 1,000-byte cap bounds the voice objective; the measured room can lower it. Return the actual byte limit on refusal and ask the operator to shorten it. Never truncate the objective or rewrite the approved core to fit.

An isolated source-derived measurement using normal canonical project/conversation handle widths gives bare rotation room of **873 / 882 / 1,129 bytes** for those three branches. With all branches reserved, the example objective ceiling is **850 bytes**. Composing that maximum with a full 4,096-byte history succeeds at 31,258 delivered bytes plus the 742-byte scaffold, with `historyDropped: true`. These observations validate the sizing mechanism; the implementation must calculate its own limit from supported identity bounds, including longer admitted identities and multibyte objectives.

Every appended byte consumes one byte of possible rotation-history space on each later rotation. The current composer drops the entire history section first, then trims optional notes; it does not trim history byte by byte (`src/lib/orchestrator/handoffDigest.ts:226`). The objective remains in the core. Appending an objective can therefore remove a whole digest; the creation readback/card explains that the successor may need to reread its predecessor. Existing rotation output already reports `historyDropped` and `notesTruncatedTo` (`src/lib/orchestrator/seatCommand.ts:1790`). Maximum-objective acceptance must exercise first and repeated rotations with full history and notes, report the trim, preserve the complete objective, and never return `too_large` for the preflighted profile/identity bounds. A later enlarged role table or scaffold still receives the normal explicit preflight refusal; a successful spawn is no promise about a changed profile.

## Execution and recovery

Extend existing call storage with the private starter session id, confirmed foreign-project set, and a small discriminated operation record: delegation versus bootstrap. Bootstrap can have a project/folder target before a recipient exists; forcing it into today's recipient-required proposal would preserve the very refusal being solved. Reuse confirmation events/cards and one resolver capable of both kinds. Store the immutable effect digest and derived registration/seat/message keys before dispatch. Deduplicate by the call, originating operator turn and normalized operation target/content, across provider call ids and reconnects. An explicit later repeat is a new operation.

Execution order: validate authority, explicit target kind, near matches and full plan → await creation confirmation → revalidate authority/plan → register folder/project → execute seat intent with the recorded key → observe mandate/launch settlement → deliver an optional task request when the seat can accept it. Revalidate human authority after awaits and at the last admission point before every effect. Serialize conflicting registrations through the shared curation writer; the existing creation route lacks an idempotency key, so add a bounded registration adapter with an operation-to-identity record and exact-root verification. A duplicate belonging to another operation returns conflict; it must not become implicit adoption.

The filesystem and seat store cannot be one atomic transaction. Persist step outcomes so a retry resumes the unfinished step with its original key. Use existing seat intents and message receipts for their own effects. If a folder registered but launch failed, keep the folder and say exactly what remains. Never delete an operator directory as compensation. If a launch or send answer is lost, recover its recorded intent/receipt; never issue a fresh key or resend to a successor while the original outcome is unknown. After a call closes, recover receipts read-only and start no new step; subsequent work requires a live authorized call. “Starting”, “mandate delivered”, “task request queued” and “task created” remain separate outcomes.

Task proof uses existing report fields. `BridgeReportV1.correlatesDirective` identifies the delivered request and `covers` holds project-scoped outcome ids; there is no task-handle field (`src/lib/bridge/types.ts:180`, `src/lib/bridge/types.ts:187`). Extend the task-request suffix, alongside today’s correlation instruction (`src/lib/voiceCompanion/admission.ts:289`), to ask the seat to include the newly created task id in `covers`. Accept “task created” only for a report correlated to that request and attributed to its proved recipient/project, with exactly one covered id resolving to a board task in that canonical project (`src/lib/tasks/types.ts:192`).

The original operation’s receipt must match recipient and message key, be `delivered`, and carry a valid `settledAt` (`src/lib/runtime/sendSettlement.ts:178`, `src/lib/runtime/sendSettlement.ts:338`). Require `settledAt ≤ task.createdAt ≤ report.at` using the server timestamps (`src/lib/tasks/types.ts:279`, `src/lib/bridge/types.ts:169`). This provides a conservative proof that the acknowledged task was created after confirmed delivery. Receipt recovery with a delayed acknowledgement can have a later settlement timestamp than actual delivery; if ordering cannot be proved, keep creation unverified. A lost response recovers the original receipt and report without another send. No new timestamp field or task snapshot is needed.

Missing `covers`, free-text claims, nonexistent ids, tasks older than confirmed delivery, foreign tasks, multiple plausible task ids and missing/late receipt timestamps leave the outcome “request sent; task creation unverified”. Speak a proved task’s safe title and project, retaining the id internally. This validates the orchestrator’s correlated acknowledgement against board state; it does not prove every requested downstream action has finished. No report-schema change or parsing of ids from prose is required. The suffix, receipt projection and outcome validator are part of slice 4.

## Numbered design options and answered operator questions

1. **Bootstrap plus orchestrator relay (selected and recommended).** Voice directly prepares confirmed project/seat creation. The target seat creates tasks and runs work; ordinary sends use current admission plus the server’s first-use foreign-target readback. This satisfies the originating requirement and preserves the earlier action decision, with asynchronous task acknowledgement.
