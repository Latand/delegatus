# Pipeline format six transition

An existing SQLite installation first deploys and verifies the format-five compatibility bridge as its serving baseline and the next release's rollback target. The bridge preserves format-six records and replay evidence while holding work it cannot execute. The feature release then performs the forward transition. After six-format writes, backout uses that verified bridge or a forward repair; a format-five-only release and a pre-upgrade snapshot are unsuitable rollback targets.

The transition recognizes only the complete `pipelines` and `pipelines_archive` pair at version five with their existing migration identities and version-six declarations. A missing or mixed pair, an unknown migration identity or an unsupported version refuses without guessing. New installations retain the ordinary first-import path.

Only the current startup owner can migrate an existing pair. Live or unidentified collection writers hold the transition; proven stale process identities remain recorded for ordinary lease recovery. The migration verifies the receipt/capacity schema, populates missing receipt projection entries from authoritative SQLite rows, rejects contradictory owners, rechecks authority, and updates both markers in one writer transaction. It rechecks publication authority again after that update. A failure rolls back projection updates and both markers together.

The migration preserves stored record tuples, collection revisions and change floors, import and mirror evidence, leases, controller queues and scheduling state. It does not replace SQLite data from JSON or rewrite payloads to fire triggers. Repeated startup after success does no migration work. Startup statements have explicit lifetime ownership for the supported older Bun runtime.

Tests exercise nonzero revisions, opaque records, retained replay keys, stale JSON, repeated startup, malformed pair metadata, wrong derived schema, a failure during the joint update, lost authority before and after marker changes, and live/unknown/reused process identities. The shared reader tests exercise the rollback contract at format five and the recognized-record contract at format six; neither mode skips its data and delivery assertions.

Private retained-copy rehearsals run the actual bridge and full reader in separate processes. They compare ordered record, metadata, change-history, controller and scheduling digests across migration, then add a format-six record, write an ordinary record through the bridge and return to the full reader. Accepted records and original/adopted replay keys must survive without relabeling the database. Synthetic journal rehearsals separately verify that the bridge retains unsent host/native input and the full reader transmits it once after recovery.
